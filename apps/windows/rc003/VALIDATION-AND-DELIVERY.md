# RC003 Windows 验证与交付分级规则

状态：已启用

最后更新：2026-08-24

本文是 RC003 Windows 项目选择复核批次、验证深度、交付级别、执行顺序和结果复用
的唯一规则正文。`AGENTS.md` 只保留入口与门禁，`README.md` 只保存命令
和使用说明，`TESTING.md` 只记录计划、结果和证据，`MAINTENANCE.md` 只保存维护批次事实。

只有任务涉及完整检查、本地测试包、候选构建、正式发布、判断已有结果能否复用，
或长任务确需分阶段和安排独立复核时才需要读取本文。普通局部修改按适用
`AGENTS.md` 做最低有效验证；仅因人工项未完成而标记“检查点待实测”，也不为形式
完整而套用本文全部步骤。

## 一、四项判断互不代替

每个任务分别判断以下四项，不得从其中一项自动推出另一项：

1. 功能影响：按根 `AGENTS.md` 判断 L1、L2、L3。
2. 验证深度：定向检查、受影响范围检查、完整检查。
3. 交付级别：不制作产物、本地测试包、正式候选、正式发布。
4. Git 状态：普通提交或“检查点 / 待实测”。

因此：

- L3 不等于正式发布；高风险修改只会扩大必要的风险验证。
- 完整自检不等于构建独立候选、ZIP、签名、上传或发布。
- 本地 ZIP 不等于正式候选或正式发布。
- 普通提交和检查点都不自动触发完整检查或打包。
- 测试项很多、任务耗时很长或使用了子任务，也不构成升级交付级别的理由。

## 二、长任务的复核与验证顺序

是否分阶段、阶段边界和当前阶段范围，以 `D:\Wuxianmai\AGENTS.md` 的“范围与阶段”为
唯一正文。
本文只补充 Windows RC003 在长任务中的复核批次、验证和交付顺序，不重复定义阶段。

独立复核只在跨模块合同、数据安全链路、真实设备风险或最终集成确有第二视角价值时
安排；L2、L3、任务很长或测试很多本身都不自动触发复核。

- 跨检查面最多安排一批轻量前置风险检查，以及一批功能冻结后的最终复核。同一检查
  面不重复安排，单函数、单入口、单文件局部修改和单一失败定位默认不拆复核。
- 前置复核只找会改变方案或阻断当前阶段的高影响风险；最终复核只看最终差异、跨阶段
  集成和此前没有覆盖的边界，不重新审计已经有充分证据且代码未变的范围。
- 已有证据足以作出判断、代码未变，或继续复核只会重复查看同一范围时必须停止。复核
  发现真实问题后，由主任务决定是否纳入当前范围，并只重跑因修改而失效的检查。

## 三、验证深度

### 1. 定向检查

适用于局部、可逆、消费者明确的修改。只检查本次函数或文件、直接调用点、同类
边界以及至少一个正常和一个失败例。单一文档修改只核对内容、引用、状态和格式。

### 2. 受影响范围检查

适用于共享组件、多个真实消费者或跨一条模块边界的修改。覆盖已确认的消费者、
关键状态、兼容路径和失败恢复，不自动扩展到无关模块或全部测试。

### 3. 完整检查

只有以下条件之一成立时执行：

- 定向或受影响范围检查无法证明修改没有破坏其它真实消费者；
- 用户明确要求“完整自检”或“全量测试”；
- 已明确进入正式候选或正式发布；
- 修改了完整测试、公开边界或候选构建本身依赖的公共合同，且不存在等价的较窄验证。

主动扩大为完整检查前，先用一句白话说明定向检查缺少什么证据。不能只因为任务是
L3、准备提交、已有完整测试入口或过去曾经跑过完整门禁就自动执行。

## 四、交付级别

### 1. 不制作产物（默认）

普通代码、测试、配置和文档任务默认停在这一层。完成相应验证后即可提交或标记
检查点，不构建冻结程序，不复制候选目录，不制作 ZIP，也不更新发布资料。

### 2. 本地测试包

只有用户明确要求本机可运行程序、测试包或本地 ZIP，或用户已授权的人工验证目标
明确要求使用冻结程序时才进入。本地测试包可以来自明确记录的工作树状态，不要求
为了打包先把其它并行任务一起提交；必须标明它不是正式候选或发布包。

本地测试包只执行得到可运行产物和证明该产物可用所必需的步骤。不得顺带创建 tag、
GitHub Release、签名、安装器、正式发布说明或自动提交。用户只说“最新程序”时，
先从当前对话和项目状态确定源码来源；只有多个来源无法判断时才询问，并且不把这句
话当作正式候选或发布授权。

### 3. 正式候选

只有用户明确要求候选版、正式测试候选或外发验收包时才进入。候选必须来自已冻结
且来源清楚的代码状态，运行完整候选构建门禁，并准确记录自动检查和未完成的真机
项目。候选可以未签名，但必须明确标注，不能冒充正式稳定版。

### 4. 正式发布

只有用户明确要求发布、上传、创建 tag / Release、签名或制作正式安装包时才进入。
发布产物必须来自确定的干净提交或 tag；安装器、便携 ZIP 与 `SHA256SUMS.txt` 必须
来自同一次 Windows CI 构建。发布说明必须如实区分自动通过、真机通过和仍未完成的
项目。

## 五、检查点不是交付阶段

“检查点 / 待实测”表示源码已经达到可独立回退的稳定状态，但仍有真实设备、宿主
软件或人工判断未完成。它可以只有定向检查，也可以已有完整检查；是否打包另行判断。

- 不因要写检查点而构建或打包。
- 不因制作本地测试包而强制新增 Git 提交。
- 普通任务按根 `AGENTS.md` 的 Git 规则提交；人工未完成时使用准确的检查点口径。
- 正式候选先冻结并提交源码，再从该提交构建，避免先构建后改变来源提交。

## 六、结果复用与失效

同一状态由源码与测试内容、锁定依赖、构建脚本、固定资产及实际产物共同确定。同一
状态已经得到成功结果时直接复用，并记录原命令、时间和来源；不要为了“最后再确认
一次”重跑同一门禁。

下列情况使对应结果失效：

- 源码、相关测试、依赖锁定、构建配置、固定资产或产物内容发生变化；
- 失败后为修复问题改变了会影响该检查的内容；
- 运行环境变化正是本次要验证的对象；
- 原结果缺少退出码、来源状态或其它足以判断是否成功的关键证据。

纯文档变化通常只需要重新核对文档；只有该文档属于本次公开边界或打包范围时，才补做
对应的边界检查。除非文档会被打入产物或改变构建输入，否则不使单元测试和冻结程序
结果失效。只改变包装文件时，不重跑与包装无关的源码测试。

## 七、构建和包装去重

`build/build-candidate.ps1` 已经依次执行：

- 公开边界检查；
- VB-CABLE 固定来源与 SHA-256 校验；
- 带资源泄漏告警门禁的完整 unittest；
- PyInstaller 冻结构建；
- 构建所得 EXE 的 `--dry-run`。

脚本对同一状态成功后，不再在脚本外机械重复公开边界、完整 unittest 或同一 EXE 的
`--dry-run`。单独运行这些命令只用于脚本未覆盖、上次结果已经失效，或正在定位脚本
内部失败的情况。

复制、ZIP 和哈希按以下方式去重：

- 构建目录复制到本地测试目录时，只做一次来源到目标的一致性验证；已经逐文件哈希
  一致，就不再为证明内容相同重复启动复制版 EXE，除非路径、权限或启动方式正是测试目标。
- 本地测试 ZIP 只需确认压缩包可打开、顶层目录和关键文件正确，并记录 ZIP 与主 EXE
  哈希；不默认做发布级完整解压和逐文件哈希。
- 正式候选或发布包应完整解压一次并逐文件核对一次。结果一致后，不再换另一种工具
  对同一份包重复同等检查。
- 产物内容或压缩工具、参数发生变化时，只重做受影响的包装与完整性检查，不重跑仍然
  有效的源码测试和 PyInstaller 构建。

## 八、推荐执行顺序

1. 先确定功能影响、稳定阶段、验证深度和交付级别。
2. 确有第二视角价值时，安排一次轻量前置风险检查；否则直接实现。
3. 按阶段完成代码修改和定向或受影响范围检查，不把后续阶段和相邻发现提前带入。
4. 功能冻结后，确有需要时安排一次最终复核；没有新增证据价值时立即停止追加复核。
5. 只修复已经确认且属于当前范围的问题，并只重跑因此失效的检查。只有达到完整检查
   条件时才执行一次完整检查。
6. 需要本地测试包时，复用同一状态的有效构建；没有可复用产物才运行构建脚本一次。
   正式候选先形成干净源码提交，再运行一次候选构建和一次必要的包装验证。
7. 代码与产物状态稳定后，一次性更新 `TESTING.md`、`MAINTENANCE.md` 或发布说明；
   不在实现中途反复改写“已完成、已通过”等正式结论。
8. 人工真机验收在有对应可运行产物后进行。普通源码任务不因待真机而阻断其它独立
   任务；只有用户要求候选收口或发布声明时，才按对应门槛判断能否宣称通过。

## 九、文档、Git 和子任务

- `TESTING.md` 只登记有复用价值的测试计划、最新结果和人工队列，条目本身不触发执行。
- `MAINTENANCE.md` 只记录重要维护批次、历史事实和来源，不要求每次局部修改都写完整
  故障、根因、文件、测试、人工验收和提交清单。
- 普通提交在本任务最低有效验证通过后进行；本地测试包不因“有产物”而自动提交；
  正式候选按上一节先提交后构建。
- 是否拆分子任务及其层级按根 `AGENTS.md` 执行。进入本文流程后，同一检查面只安排
  一次；子任务只交付指定结论和证据，不得自行转入实现、正式文档、完整检查、构建、
  打包或发布；是否采纳发现、是否扩大范围由主任务判断。
- 子任务结论由主任务合并核对一次。不能因为使用了子任务就把每个结论再次交给新的
  子任务复审，或重复整套测试；证据已经足够后停止追加子任务。

## 十、不得放松的安全边界

- 真实用户配置、日志、蓝牙配对、音频端点、驱动、权限、密钥、签名材料和既有发布
  产物仍按适用 `AGENTS.md` 默认只读。
- 正式候选和发布继续执行公开边界、固定第三方资产哈希、来源提交和产物完整性检查。
- 未签名产物必须明确标注；没有完成的真机、宿主软件、休眠恢复、长期运行或杀软兼容
  验收必须如实列出，自动测试不能代替。
- 发布或分发继续遵守 GPL-3.0-only，并保留归属、版权和第三方通知。
- 任何失败检查都不得被“为了快”跳过；应修复、明确降级为非候选本地测试包，或报告
  阻塞，不能把失败结果写成通过。
