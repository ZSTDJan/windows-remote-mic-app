# BUG-027：语音长按结束后按键或鼠标持续连按

状态：已修复并通过真机复测，2026-08-30 收口。

记录日期：2026-08-30

## 问题边界

使用 RC003 按住说话并松手后，随后输入的字母可能像被长按一样连续出现，鼠标操作
也可能表现异常；语音结束后还可能短暂卡顿。搜狗和微信输入法都出现过，因此这不是
某一个输入法的文字上屏或粘贴问题。

本问题和“Alt 键锁死”表现相似，但当前已确认的触发链路更具体：一次语音手势被
过早结束，迟到的 HID 按下被误当成下一轮，程序向宿主多发了一个没有匹配抬起的
快捷键按下。以后若问题发生在语音长按之后，优先从本文件拾起；与语音无关的
Ctrl、Alt、Win 残留仍从 `Alt键锁死问题.md` 拾起。

## 已确认现场

两台机器的黑匣子记录都能稳定得到以下顺序：

```text
AudioStarted -> F5 down -> AudioStopped -> 迟到 Raw Input mic down -> F5 up
```

旧逻辑在 `AudioStopped` 到达时立即结束旧手势。随后到达的 Raw Input mic down
被当成新一轮并再次发送宿主 DOWN，但该轮没有对应的 HID up，因此留下按键按住状态。
长按会拉大音频、Raw Input、HID tap 和 legacy F5 的到达间隔，所以更容易触发，
但长按本身不是另一个根因。

## 修复合同

- legacy F5 只负责吞掉原生 F5 并附着到已有语音手势，不得启动、发送或释放宿主
  语音快捷键。
- `AudioStopped` 不能单独把仍有物理来源的手势判定为结束；迟到 HID down 必须并回
  旧轮，不能开启新一轮。
- 只有本轮已经记录过 down 的 HID/HID tap up 才有释放资格；游离 up 不改变宿主
  按键状态。
- 已隔离的迟到 F5 up 必须先于设置热加载、普通映射和按键检测消费，不能串入下一轮。
- 语音中途发起按键检测时，本轮语音收尾优先，检测请求留给下一次独立按键。
- cleanup 与 F5 回调交错时必须重新核对输入代次，旧连接事件不能污染新连接。

当前主要实现入口在 `src/ovb_rc003/app.py`：

- `_finish_voice_mic_gesture`
- `_handle_key_detection_mic_event`
- `_dispatch_legacy_key_event`
- `_cleanup_once`

## 复发后如何拾起

先确认是否同时满足“使用语音长按”和“松手后键盘或鼠标持续按住”。满足时不要先
归因给输入法、UU 远程或剪贴板，也不要盲目补发 Alt up。保留以下最少证据：

1. 复发的准确时间，至少精确到秒；记录长按时长、使用的输入法、远程软件和下一步
   触发异常的键盘或鼠标动作。
2. 当时运行的 `RemoteMicRC003.exe` 完整路径和 SHA-256；不要只写“最新版本”。
3. 主控端与被控端对应时间前后至少 10 秒的黑匣子 session ZIP 和 Remote Mic 日志。
4. 核对宿主快捷键 DOWN/UP 是否成对，并搜索上述五段事件顺序；同时确认迟到 HID
   是否被并回旧手势、迟到 F5 up 是否先被隔离消费。
5. 先复跑 `tests/test_app_wiring.py` 中与 `late`、`retired_f5`、`audio_stop`、
   `detection_requested_mid_voice` 和 cleanup 相关的回归，再根据新日志决定是否改代码。

只有新日志再次证明宿主 DOWN 没有匹配 UP，或旧手势结束后迟到来源又开启新轮，才
重新打开本问题。不要退回“仅靠 `AudioStopped` 结束手势”、让 F5 重新取得宿主快捷键
发送权，或用固定延时掩盖来源乱序。
