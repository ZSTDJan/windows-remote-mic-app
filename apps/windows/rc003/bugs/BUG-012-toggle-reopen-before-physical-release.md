# BUG-012 切换模式续开早于实体松键导致首次短按无声

状态：自动验证通过，`fix12` 待本机真机复测

记录日期：2026-08-21

代码修复提交：`f6ae3c3`

## 现象

用户在 `fix11` 使用“按一下切换”时，第一次短按麦克风键可以唤起宿主语音，
但松开后讲话没有反应；必须先持续按住一次，按住期间才能得到识别。长按之后
状态偶尔继续存活，下一次实体按键才会改变或关闭它。

按键识别、CABLE Input / Windows WASAPI、宿主快捷键和长按期间的 PCM 均已
分别证明可用，因此本轮继续核对设备开关麦命令与实体 F5 释放的相对时序。

## 本机日志证据

2026-08-21 15:39:44 的第一次短按中：

1. `AudioStarted` 于 15:39:44.023 到达；
2. PCM 于 15:39:44.370 开始，短流共 255 毫秒；
3. `AudioStopped` 于 15:39:44.618 到达，旧逻辑同一时刻续发 `MIC_OPEN`；
4. 设备于 15:39:44.648 回复续流 `AudioStarted`；
5. 实体 F5 直到 15:39:44.726 才真正 up，比续开晚约 108 毫秒；
6. 该续流没有任何 PCM，直到下一次实体按键。

2026-08-21 15:40:11 的长按中，原始实体按压产生约 3225 毫秒 PCM，汇总为
`result=signal`。这证明音频端点和解码链路能够工作；区别在于第一次短按的
主动续开命令发在实体释放收尾阶段，而不是用户是否讲话。

记录不包含设备地址、设备路径、身份 ID 或语音内容。

## 根因

旧 TOGGLE 路径在收到 `AudioStopped` 后立即调用
`send_mic_open_threadsafe()`。真机事件表明 RC003 的音频停止通知可以早于
legacy F5 / HID 的最终松键边沿；此时设备仍在处理原始物理手势。设备会回复
新的 `AudioStarted`，但不会继续发送 PCM，相当于过早的续开命令被实体释放
收尾吞掉或进入空流。

仅把命令固定延迟若干毫秒仍不完整：不同机器可能先收到音频停止、再收到迟到
的 F5/HID down。若此时已释放跨来源手势门闩，迟到的同一次按键还会被误判
为第二次点击关闭。

## 修复设计

- `AudioStopped` 后不再立即续发 `MIC_OPEN`，而是进入“待续开”状态。
- 已观察到实体来源 down 时，等待全部 legacy F5 / HID 来源 up；最后一个
  up 到达后才把续开放到应用事件循环执行。
- 实体来源已经完整释放时立即排队续开；完全没有物理边沿的 BLE-only 路径
  等待 200 毫秒，吸收可能迟到的来源后再兜底续开。
- 宽限期间保留当前跨来源手势，迟到的 down 只加入原手势，不会触发第二次
  TOGGLE；最终 up 后仍只续开一次。
- 第二次点击关闭、连接清理或重连会按 generation 取消待续开和计时器；旧
  回调不能向新连接发送 `MIC_OPEN`。
- 低层 F5 钩子仍只投递事件；延迟与设备命令均由应用事件循环处理，不在
  钩子线程中等待或执行阻塞工作。
