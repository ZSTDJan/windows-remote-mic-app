# BUG-017：RC003 开关型持续语音的固件边界

状态：HOLD 产品路径已确认；严格 On-request 专项探针已实现，真机结论待回传；
TOGGLE 不能再标记为已修复，产品取舍待决定。

## 用户现象

- “按住型语音”在先长按后能够取得非零 PCM 和识别文字。
- “开关型语音”第一次短按可以唤起宿主，但松开后没有可识别语音。
- Windows 端多轮修复已经消除了过早续开、重复来源、F5 回声和配置未热加载，
  但主动续开的会话仍可能只有 `AudioStarted`、没有 PCM。

## 产品与上游证据

截至 2026-08-21 可核验的产品相关资料一致指向：RC003 的可靠原生语音行为是
按住语音键传音、松开停止。

- 小米官方页面确认“小米蓝牙遥控器 2 Pro”这一产品及公开规格；RC003 型号
  对应关系来自本项目设备资料。官方页面没有给出 Windows 麦克风或免按持续
  录音能力说明。
- `HD838A/remote-mic-app` 截止提交 `e7dd86e` 的 README 明确要求持续按住
  RC003 语音键，并说明固件会在松开时停止麦克风音频。
- 同一上游的真机实验记录更直接：用 Power 触发主机主动 `MIC_OPEN` 时，
  设备返回 session 0 的开始控制事件，但整个会话没有 audio characteristic
  数据；同一 BLE 连接随后按普通语音键立即出现连续 120-byte 音频包。上游
  已撤下该持续录音实验，不能把控制层“已开始”当成真实收音成功。
- `nijez/open-voice-bridge` 的 RC003 使用说明同样是按住麦克风键讲话。

因此，现有 Windows TOGGLE 策略“先按普通语音键取得短 HTT 会话，松开后再
主动 `MIC_OPEN` 续流”没有产品级证据支持。继续只调 100/200/250 毫秒等待
不会让固件凭空产生音频。

## 协议仍保留的一条窄路径

ATVV v1.0 的通用 On-request 交互模型并不等于 RC003 已实现持续录音。规范路径
是设备先因实体按键发送 `START_SEARCH`，主机随后发送 `MIC_OPEN`，之后才是
`AUDIO_START` 和音频流。

本地 On-request-only 探针已经验证：RC003 接受 interaction `0x00` 协商；直接
发送 `MIC_OPEN` 会返回 reason 0、stream 0 的 `AUDIO_START`，但等待四秒仍
为零 PCM。该探针没有先制造规范要求的实体 `START_SEARCH`，因此目前唯一尚未
排除的窄路径是：

1. 只协商 On-request；
2. 实体短按语音键，确认收到 `START_SEARCH`；
3. 主机立即回复 `MIC_OPEN`；
4. 松开后讲话 2 至 3 秒；
5. 第二次短按或主机 `MIC_CLOSE` 结束；
6. 检查 PCM 数量、stream id、开始/停止 reason。

只有这条真机链出现持续非零 PCM，才有继续产品化 TOGGLE 的依据。若设备仍走
普通 HTT 的 `AUDIO_START -> AUDIO -> AUDIO_STOP`，或主动开始后仍为零 PCM，
就应把 RC003 正式能力收敛为 HOLD。

## 2026-08-22 专项诊断实现

新增隐藏入口 `--on-request-probe` 和便携启动脚本
`Run-OnRequest-Probe.cmd`，只验证上述最后一条窄路径：

1. 使用与正式桥接相同的单实例互斥锁，拒绝与后台桥接同时占用设备；
2. 只协商 On-request，不启动 HID、宿主快捷键、PortAudio 或 VB-CABLE；诊断
   生命周期内只启动一个窄范围 F5 guard，吞掉 RC003 话筒键泄漏到前台的 F5，
   不替换成任何宿主快捷键；
3. 等待实体 `START_SEARCH` 后只发送一次 `MIC_OPEN`；
4. 第二次有效 `START_SEARCH` 只发送一次 `MIC_CLOSE`；
5. 最多观察 18 秒，只记录控制事件、PCM 批次/样本计数和相对时间，不保存
   蓝牙地址、设备路径、语音样本或转写内容；
6. 结果写入
   `%LOCALAPPDATA%\RemoteMic\RC003\logs\on-request-probe-result.json`。

成功判据不能只看总 PCM 或“超过一秒仍有声音”。只有设备先报告
`AUDIO_START reason=MIC_OPEN, stream_id=0`，且该主机开麦会话自身在开始一秒
后仍有 PCM，才分类为 `pcm_continued_past_1000ms`。普通 HOLD/HTT 长按产生的
音频、主机开麦只有控制事件、开麦流提前停止以及无 `START_SEARCH` 均不能误判
为成功。

自动验证为 1171 项通过、7 项安全或平台条件跳过；公开边界扫描 276 个文件、
`compileall`、`pip check` 和 `git diff --check` 通过。以上只证明探针实现和
隐私/构建边界，真实 RC003 结果仍待用户运行便携诊断包后回传。

2026-08-22 用户指出旧探针退出桥接后会把话筒键原生 F5 泄漏到记事本并插入
日期。根因是旧探针只占用 BLE，没有像正式桥接那样启动 F5 guard。探针现已在
自身完整生命周期内临时吞掉 F5；启动、正常结束和异常清理都由定向测试覆盖。

## 当前代码边界

- 保留现有 TOGGLE 代码，避免在没有用户产品决策时擅自删除配置和迁移路径。
- TOGGLE 必须标为实验/待验证，不能在变更记录、台账或候选说明中声称完成。
- 专项探针是一次性能力判断工具，不属于设置界面或正式后台桥接功能；真机
  结论形成后应按结果决定 TOGGLE 的去留，而不是长期扩展探针本身。
- `BUG-016` 的音频停止排序修复仍然有效：它保护 RC003 已经真实发送的短音频，
  但不能解决固件不发送音频的主动会话。
- 不新增 HTTP、URL Scheme、Quicker 深度集成或与本问题无关的语音状态机重写。

## 待用户决定

   长时、断连、休眠和电量验收。
2. 探针失败：界面隐藏或移除 RC003 TOGGLE，只正式支持 HOLD；配置迁移和
