# BUG-019：旧蓝牙候选检测卡住并长期占用桥接实例

状态：根因确认并修复，自动回归通过，等待同机多候选真机复测。

## 用户现象

- 2026-08-22 22:42 从通知区域退出桥接后运行 On-request 专项检测；检测停在
  寻找 RC003，之后再次运行只得到 `bridge_already_running`。
- 此时重新打开设置并点击启动桥接，通知区域没有图标；普通按键仍会直接作用
  于前台文本，但设置页无法检测和高亮真实遥控器按钮。
- 结果文件中的 `capabilities`、`events` 和 `pcm` 均为空，证明该文件来自后续
  被单实例保护拒绝的第二次启动，不是一次完整能力检测。

## 日志证据与根因

- `22:42:35.149` 第一份专项检测已经取得单实例锁并启动 F5 拦截；
- `22:42:37.527` 发现两个 RC003 名称匹配候选并开始逐个检查语音服务；
- 此后没有任何候选完成或超时日志；
- `22:44:01.081` 和 `22:44:28.472` 是用户再次运行检测，被第一份仍存活的
  检测进程拒绝。

候选检查原本使用 `asyncio.wait_for(..., timeout=8)`。Windows 的某些蓝牙
异步调用面对旧配对记录时不会完成取消；`wait_for` 到点后仍会等待底层取消
结束，因此名义上的八秒超时可能无限延长。第一份检测一直持有单实例锁和 F5
拦截，后续桥接与按键检测便无法启动。

## 修复

- 默认的真实候选检查改在守护线程的私有事件循环中运行，只把设备标识字符串
  传入线程；主桥接循环按八秒真实截止，不再等待失效的系统取消。
- 一个候选超时后按不可达处理，并继续检查后面的候选；恰好一个可达时仍按原
  安全规则选择，零个或多个可达仍失败关闭。
- 同一进程中如果某个旧候选的守护线程仍未返回，不重复为它创建更多线程。
- 日志仍只记录候选序号、总数、可达结果和异常类型，不记录设备标识。
- `bridge_already_running` 提示改为明确说明占用者可能是后台桥接，也可能是
  上一次尚未结束的专项检测。

## 真机复测

1. 保持当前 Windows 返回两个 RC003 候选的状态，不再删除设备。
2. 从通知区域退出桥接，运行专项检测。
3. 检查每个候选最多约八秒后都出现结果或超时日志，程序不再无限停住。
4. 检测结束或失败后立即重新启动桥接，通知区域图标和真实按键检测必须恢复。
