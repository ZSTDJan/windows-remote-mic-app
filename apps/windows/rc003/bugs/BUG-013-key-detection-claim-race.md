# BUG-013 并发按键来源可能同时认领失败

状态：自动验证通过

记录日期：2026-08-21

代码修复提交：`cfbca35`

## 发现经过

`fix12` 第一次候选构建被完整测试门禁停止：
`test_only_one_concurrent_button_can_claim_a_request` 得到 `[False, False]`，
而一次检测请求应当恰好由一个按键来源认领。单独连续运行 30 次时复现 3 次，
证明不是构建输出噪声，而是可重复的并发缺口。

该问题不涉及语音状态机，但会造成设置页“检测真实按键”偶发没有任何来源
成功回传结果，因此不能通过简单重跑构建掩盖。

## 根因

`publish_next_button()` 原本让每个事件线程先读取同一个请求 JSON，再竞争
独占 claim lock。Windows 上胜者取得 lock 后准备把 request 原子移动到
claimed 路径时，败者可能仍持有短暂的读取句柄；胜者的 `os.replace()` 因
共享冲突失败，败者又因 lock 已存在返回失败，最终两个来源都返回 `False`。

结果写入失败时旧逻辑还会删除 claimed 文件，无法把尚未完成的请求交给
后续来源重试。

## 修复设计

- 仅从请求文件名构造候选 token，先用 `O_CREAT | O_EXCL` 获取 claim lock。
- 只有 lock 所有者才读取、校验并移动请求 JSON，其他来源不再并发打开它。
- 结果原子写入失败时尽量把 claimed 文件恢复为 request；认领锁始终在
  `finally` 中释放。
- 保持一次性语义：成功结果仍只有一个，其他并发来源返回 `False`。
