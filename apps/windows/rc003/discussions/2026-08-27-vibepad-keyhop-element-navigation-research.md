# RC003 元素导航：VibePad 与 Keyhop 深挖记录

日期：2026-08-27

状态：调研和独立键盘原型完整检查完成；可进入受控应用试用，正式 RC003 接入待确认

范围：Windows RC003 使用按钮在固定软件的按钮、输入框、列表项等可交互元素之间导航

## 1. 结论先行

目标可行，但不建议现在从零写一套“遥控器鼠标”。现成能力的最优使用顺序是：

1. **先原样试用 Keyhop**，用 RC003 触发元素提示，再用 8 个遥控器组合输入提示字母；
2. UIA 覆盖率够用后，**给 Keyhop 增加很小的外部触发入口**，去掉对全局快捷键的依赖；
3. 最终需要电视式上下左右时，**保留 Keyhop 的元素识别、过滤、覆盖层和执行动作，新增空间导航状态机**；
4. VibePad 适合借鉴交互和方向评分，但不适合直接作为依赖，也不能在许可不明时复制代码。

两者并不是同一类成品：

- VibePad 已经做出“蓝框选中一个元素，方向键移动，确定点击，返回退出”的电视式体验，
  但导航部分仍明确标为测试版，浏览器兼容、元素漏识别和跳转异常均是已知问题；
- Keyhop 只做“给所有元素贴字母标签，输入标签后执行”，不是方向导航，但元素识别、过滤、
  浏览器唤醒、缓存、多屏覆盖和动作执行明显更完整，且许可清楚、发布与自动测试更成熟。

因此，**交互参考 VibePad，工程底座优先 Keyhop**。

## 3. 目标交互到底是什么

用户要的不是让光标每次移动几像素，而是像电视遥控器：

```text
进入元素导航
  -> 当前按钮出现明显选中框
  -> 上 / 下 / 左 / 右跳到视觉上最近的可操作元素
  -> 确定执行按钮、勾选框、标签页或输入框的主操作
  -> 返回关闭弹窗、退回上一层或退出导航
  -> 音量键可在导航模式中临时改为滚动
```

这种方案的优势是：不要求用户看见小鼠标指针，也不要求遥控器具备摇杆；固定软件的
布局越稳定，越容易通过 UIA 元素和少量应用规则把体验做稳。

它依赖目标软件把界面正确暴露给 Windows UI Automation。标准按钮、输入框、菜单、
列表、树、标签页通常较好；游戏画面、自绘 Canvas、远程桌面画面、视频画面和没有
无障碍语义的自绘控件，可能只表现为一个大矩形，无法识别内部按钮。

## 4. VibePad 深挖

### 4.1 它已经实现的电视式体验

VibePad 的 `Navigator` 分三级：

- Level 1：在顶层窗口和任务栏之间导航；
- Level 2：进入选定窗口后，在可交互 UIA 元素之间导航；
- Level 3：点击可编辑控件后进入输入状态，方向导航暂时锁定。

主要动作已经覆盖遥控器需要的语义：

- 上下左右移动焦点；
- 点击、双击、右键；
- 返回层级或发送 `Esc`；
- `Tab`、`Enter`；
- 滚动、切换标签页、打开系统屏幕键盘；
- 蓝色透明置顶焦点框，且覆盖层允许鼠标穿透。

这套交互说明“只识别页面元素、用按钮导航”不是概念验证，而是已经有可运行实现。

### 4.2 方向选择算法

VibePad 不调用控件自身的 Tab 顺序，而是按屏幕矩形做空间选择：

1. 先排除中心点不在目标方向的元素；
2. 计算主轴距离，例如向右时主要看目标中心比当前中心右移多少；
3. 加上 `0.3 ×` 侧向偏差，避免跳到斜得太远的元素；
4. 减去 `0.5 ×` 两个矩形在侧向轴上的重叠量，优先选择同行或同列元素；
5. 得分最低的元素成为下一焦点。

源码等价公式是：

```text
score = 主轴距离 + 0.3 * 侧向偏差 - 0.5 * 侧向重叠量
```

优点是实现简单、容易解释，按钮网格和常规表单上通常自然。缺点是它没有处理全部
空间导航难题，例如滚动容器边界、跨区跳转、遮挡、层级弹窗、逻辑顺序、循环导航和
布局变化后的焦点恢复。README 所说的“偶发焦点跳转异常”与这些边界一致。

### 4.3 元素扫描与浏览器处理

桌面软件按 UIA `ControlType` 过滤按钮、输入框、列表项、菜单项等控件。浏览器采用
多条回退路径：

- 从浏览器内容容器查找 `DocumentControl`；
- 枚举 `Chrome_RenderWidgetHostHWND` 子窗口；
- 从浏览器 UIA 树查找渲染宿主；
- 最后从窗口根递归扫描；
- 浏览器网页最多递归 24 层，普通桌面软件通常最多 8 层。

README 推荐 Edge，并要求 Chrome 通过 `--force-renderer-accessibility` 开启网页内容
可访问性。当前实现没有 Keyhop 的 `WM_GETOBJECT` 主动唤醒，因此 Chrome 的开箱体验
更依赖浏览器启动参数和当前无障碍树状态。

元素列表进入窗口时同步扫描，之后方向移动直接使用缓存，响应会很快；但页面滚动、
弹窗打开、列表虚拟化或布局变化后，如果没有及时重扫，焦点矩形和真实元素可能失步。

### 4.4 执行动作

点击采用多重回退：

1. `uiautomation` 的 `Control.Click()`；
2. `InvokePattern.Invoke()`；
3. 元素中心坐标模拟鼠标点击。

这个顺序不如 Keyhop 完整。对复选框、单选项、标签页、树展开器等控件，直接点击通常
能用，但没有优先调用 `Toggle`、`SelectionItem`、`ExpandCollapse` 等对应 UIA 模式。

### 4.5 接入 RC003 的现实问题

VibePad 的正式输入源是游戏手柄。`--mock` 只是开发用键盘模拟：

- 用全局低层键盘钩子把键盘转成虚拟手柄事件；
- 钩子最后继续调用 `CallNextHookEx`，不吞掉原按键；
- 因此 RC003 若通过 Windows 注入键盘来驱动 mock，目标软件也会同时收到这些键。

这会产生方向键既移动 VibePad 焦点、又改变目标软件自身选择的问题，不适合作为正式
桥接。要真正接入，需要新增独立 IPC、命名管道、本地套接字或直接在 Remote Mic 中
承载导航器，而不是长期依赖 `--mock`。

### 4.6 权限、质量与许可

- 程序启动时主动请求管理员权限，主要为了点击 Windows 屏幕键盘等高完整性目标；
- README 已明确导航模式存在浏览器不稳定、元素识别不全和跳转异常；
- 仓库有 58 个 Python 测试，但集中在手柄解析、按键、鼠标和模式引擎，没有
  `navigator.py` 的自动测试；
- 没有 GitHub Actions 工作流；
- README 显示 MIT 徽章并链接 `LICENSE`，但仓库实际没有 `LICENSE` 文件；
- GitHub 的 Issue 创建入口当前被限制，外部用户无法正常提交问题。

因此可以研究行为和算法思路，但在作者补齐许可证前，**不能把源码直接复制进 GPL
项目，也不应把它作为正式二进制依赖交付**。

## 5. Keyhop 深挖

### 5.1 它真正擅长的部分

Keyhop 的默认流程是：

```text
Ctrl+Shift+Space
  -> 枚举当前前台窗口的可交互元素
  -> 给每个元素显示短字母标签和目标轮廓
  -> 用户输入标签
  -> 执行元素主操作
```

它没有“当前选中元素”和方向图，因此不能直接用上下左右。但它解决了更难的一半：
在真实 Windows 软件中找到尽可能准确、可执行、不过度重复的目标元素。

### 5.2 元素识别比 VibePad 成熟在哪里

Keyhop 在一次 UIA 请求中预取边界、名称、控件类型、是否可用、是否离屏、是否可聚焦
以及动作模式，减少跨进程 COM 往返。主要过滤和兼容能力包括：

- 标准 `Button`、`Hyperlink`、`Edit`、`CheckBox`、`RadioButton`、`ComboBox`、
  `MenuItem`、`TabItem`、`ListItem`、`TreeItem`、`DataItem`；
- 自定义控件若暴露动作模式，也可进入候选；
- 浏览器中结合控件类型、UIA 动作模式、MSAA/IAccessible 角色和
  `IsKeyboardFocusable` 识别网页控件；
- 过滤过小噪点、超大布局容器、离屏或禁用元素；
- 对嵌套且视觉重复的父子元素做去重；
- 普通桌面树深度上限 12，浏览器上限 32，元素数量还有硬上限；
- 桌面软件优先用 UIA 服务端 `FindAll + CacheRequest`，失败再递归；
- 多窗口范围按进程组并行扫描，避免同一应用的 COM 对象跨线程乱用。

这部分更适合作为未来空间导航的底座，而不是重新从 VibePad 的简单递归扫描开始。

### 5.3 浏览器、缓存与覆盖层

Keyhop 会向 Chromium 渲染子窗口发送带超时的 `WM_GETOBJECT`，主动促使 Chrome、
Edge、Brave、Opera、Vivaldi、Arc 建立网页无障碍树，然后再进行 32 层扫描。这比要求
用户手工给 Chrome 加启动参数更适合普通用户。

性能方面已有：

- 前台窗口变化和元素位置变化的 WinEvent 预热；
- 默认 500 ms 的元素树缓存；
- 持久化覆盖层窗口和位图缓冲，避免每次重新创建；
- 虚拟桌面、多显示器和 Per-Monitor DPI 处理；
- 标签避让、目标轮廓和必要时的连接箭头；
- 滚轮发生后立即取消覆盖层，避免页面滚动后标签留在旧位置。

这些看似是视觉细节，实际都是遥控器体验能否稳定的重要基础。

### 5.4 动作执行

普通确定操作不是一律鼠标点击，而是依次尝试：

1. `InvokePattern`；
2. `TogglePattern`；
3. `SelectionItemPattern`；
4. `ExpandCollapsePattern`，只展开，不在普通确定时意外折叠；
5. Legacy IAccessible 默认动作；
6. 全部失败才在元素中心模拟左键。

这能更准确处理按钮、复选框、单选项、标签页、列表选择和下拉框，也减少移动真实鼠标
光标的次数。`Ctrl + 最后一个提示字母` 用于双击，`Shift + 最后一个提示字母` 用于
右键；两者都采用真实 `SendInput` 鼠标事件。

### 5.5 外部触发边界

当前 Keyhop 只公开三类用户入口：

- 全局快捷键：选元素、选窗口、打开设置；
- 托盘菜单；
- 命令行 `--close` / `--quit`。

它确实有一个隐藏 Win32 IPC 窗口，但只接收 `WM_CLOSE`，**不能从 Remote Mic 直接发
“开始选元素”“输入某个标签”“执行当前元素”**。因此原样使用时必须由 RC003 注入
Keyhop 的全局快捷键和提示字母。

少量适配最值得做的是扩展这个现有 IPC，而不是另起一套服务：

- 增加 `--pick-element` 或自定义窗口消息，直接触发元素枚举；
- 后续再增加 `move-up/down/left/right`、`activate`、`back`、`scroll`；
- 入口仍限制在当前用户会话，不开放网络端口；
- Remote Mic 只负责把 RC003 语义动作发给 Keyhop，不接管 UIA 树。

这样能保留清晰的进程边界，也避免用注入快捷键触发另一个辅助工具。

### 5.6 当前源码中已确认的缺陷和限制

1. **提示字符设置与实际输入不一致。** 设置和 README 暴露数字、`;`、`'`、自定义
   字符，但覆盖层的 `key_down()` 只接受 `VK_A..VK_Z`。因此数字和标点标签当前无法
   正常完成选择。RC003 首轮只能使用 8 个纯字母，例如 `asdfghjk`。
2. **v0.5.0 发布说明把修饰键写反。** 发布说明写 `Shift=双击、Ctrl=右键`，源码、
   README 和 CHANGELOG 的真实行为是 `Ctrl=双击、Shift=右键`。
3. **安装权限文档不一致。** v0.5.0 发布说明和当前 WiX 配置是按用户安装、无需提权，
   README 安装段仍保留“每机安装、UAC 一次”的旧说明。
4. **标签不是稳定元素编号。** Issue #25 指出重新打开后标签可能随枚举顺序变化；因此
   不适合把某个业务按钮永久记成固定字母。
5. **修饰键会影响目标应用。** Issue #25 指出双击/右键所用 Ctrl、Shift 可能和目标
   软件自身的 Ctrl/Shift 点击语义冲突。遥控器普通确定不使用修饰键，可避开这一点。
6. **仍会漏掉特定软件。** Issue #27 报告 IntelliJ IDEA 2025.3.3 中找不到任何元素。
   这说明即使 UIA 策略较成熟，也必须按目标软件实测，不能把“支持 Windows”理解成
   所有软件都可用。
7. **Firefox 网页内容仍未正式支持。** 当前主要覆盖 Chromium 系浏览器。

### 5.7 权限、质量与许可

- Keyhop 没有 `uiAccess=true` 清单，也不默认以管理员身份运行；
- Windows UI Automation 安全规则决定了普通完整性进程不能完整控制更高完整性进程，
  特别是向管理员程序回退发送鼠标和键盘输入时会受 UIPI 限制；
- 因此目标软件若以管理员运行，Keyhop 也需要相同权限运行，或者未来走签名、可信位置
  和 `UIAccess` 的正式方案，不能假设普通进程一定可控；
- 仓库为 MIT 或 Apache-2.0 双许可，可在保留版权和许可证的前提下修改和分发；
- 有 Windows CI、发布 EXE/MSI/SHA256，源码中有 92 个单元测试；
- 自动测试主要覆盖标签生成、覆盖层布局、热键解析、缓存、配置和字母表，真实 UIA
  软件兼容仍需要实机矩阵。

## 6. 两者对比

| 维度 | VibePad | Keyhop | 对 RC003 的意义 |
| --- | --- | --- | --- |
| 电视式方向导航 | 已实现 | 没有 | 交互参考 VibePad |
| 元素识别 | 基础类型递归扫描 | 缓存预取、模式/角色/焦点启发式、去重 | 底座优先 Keyhop |
| 浏览器 | Edge 较好；Chrome 常需启动参数 | 主动唤醒 Chromium UIA 树 | Keyhop 更适合普通用户 |
| 动作执行 | Click、Invoke、坐标点击 | Invoke、Toggle、Select、Expand、Legacy、鼠标回退 | Keyhop 语义更准确 |
| 布局变化 | 方向移动使用缓存，容易失步 | 覆盖层期间滚动即取消；有短缓存与预热 | 最终方向导航仍需补重扫策略 |
| 外部控制 | 无正式 IPC；mock 不吞键 | 只有关闭 IPC；其余依赖全局快捷键 | 两者都需适配 |
| 多屏和 DPI | 基础覆盖层 | 虚拟桌面、Per-Monitor DPI、标签避让 | Keyhop 更成熟 |
| 自动测试/CI | 导航器无测试、无 CI | 92 个单测、Windows CI | Keyhop 风险更低 |
| 许可 | README 写 MIT，但许可证文件缺失 | MIT 或 Apache-2.0 | 只能直接复用 Keyhop |

## 7. RC003 现有能力如何先用起来

RC003 现在已经有一个类似 Fn 的“遥控器组合”层：

- 组合主键只能选 `TV`、`菜单` 或 `主页`；
- 第二键共 8 个：上、下、左、右、确定、返回、音量加、音量减；
- 每个组合可发送普通动作、电脑快捷键或 Quicker URI；
- 命中组合后，不再执行主键和第二键原本的单键动作。

这正好能给 Keyhop 提供 8 个提示字母。建议首轮只做一套临时测试映射：

| RC003 操作 | 临时动作 |
| --- | --- |
| `TV` 单击或其它未占用手势 | `Ctrl+Shift+Space`，打开 Keyhop 元素提示 |
| `菜单 + 上/下/左/右/确定/返回/音量+/音量-` | 依次输入 `a/s/d/f/g/h/j/k` |
| 电源键 | `Esc`，取消 Keyhop 覆盖层 |

如果 `菜单` 本来有重要用途，可把组合主键换成 `主页`。关键约束是：打开 Keyhop 的
动作不能占用同一个组合主键，否则 8 个字母输入层会不好进入；也不要使用数字、标点
或修饰字母动作。

预期使用过程：

```text
按 TV -> 屏幕出现 Keyhop 字母标签
按 菜单+某个第二键 -> 输入第一个字母
如标签有两位，再按一次 菜单+某个第二键 -> 完成选择并执行
按 电源 -> 取消
```

这不是最终电视式导航，但能以最少改动验证最关键的事实：目标固定软件能否被 UIA
正确识别、标签是否可读、操作能否执行、响应速度是否可接受。

## 8. 三档落地方案

### 8.1 A 档：原样使用 Keyhop

改动：不改 Remote Mic 代码；用户安装 Keyhop，只配置 RC003 映射和 Keyhop 的 8 字母
提示表。

能得到：

- 按遥控器打开元素标签；
- 用组合键输入一到多位标签；
- 确定按钮、输入框、列表项、标签页等元素；
- 立即建立目标软件兼容清单。

局限：

- 不是方向导航；
- 标签会变化，需要看屏幕选字母；
- 依赖注入快捷键能触发 `RegisterHotKey`，这一点必须真机验证；
- 两个工具分别启动、配置和更新。

建议：**先做。** 它是成本最低、信息价值最高的验证。

### 8.2 B 档：少量适配 Keyhop

改动：维护一个 Keyhop 分支，扩展现有隐藏窗口 IPC，至少支持直接“开始选元素”和取消；
Remote Mic 增加一个明确的外部工具动作，不再通过全局快捷键唤起。

能得到：

- 启动和触发更稳定；
- 可以检测 Keyhop 是否运行、版本是否兼容；
- 避免全局热键冲突；
- 为将来的方向命令留下进程边界。

局限：仍然是标签选择；需要维护第三方分支、安装和版本匹配。

建议：只有 A 档证明 UIA 覆盖率够用后再做。

### 8.3 C 档：Keyhop 底座 + 空间导航

改动：在 Keyhop 分支或独立 Rust 辅助进程中增加：

- 当前元素状态；
- 上下左右空间评分；
- 单元素焦点框；
- 确定、返回、滚动；
- 页面变化重扫和焦点恢复；
- 面向 Remote Mic 的本地 IPC。

空间导航算法可以独立依据 W3C Spatial Navigation 和实测重新实现，不复制 VibePad
源码。第一版可使用“方向过滤 + 主轴距离 + 侧向偏差 + 重叠奖励”，但必须补充：

- 弹窗出现时只在最上层弹窗导航；
- 页面滚动或元素位置变化后重扫；
- 原元素消失时按 AutomationId、Name、ControlType 和邻近矩形恢复焦点；
- 输入框内方向键默认交给输入框，不强行移动元素焦点；
- 没有候选元素时可选择滚动或保持原位，不跨屏乱跳；
- `Esc` 优先关闭弹窗或退出导航，不模拟浏览器后退；
- 同一布局可选循环，普通表单默认不循环。

建议：这是最终产品方向，但不是首个实施动作。

## 9. 固定软件应利用的优势

完全通用的空间算法很难处理所有界面。我们主要面对相对固定的软件，可以在通用 UIA
底座上增加很薄的应用配置，而不是为每个软件重写自动化脚本：

- 用进程名和窗口特征识别目标软件；
- 优先使用稳定的 `AutomationId`，其次才是 Name、ControlType 和矩形；
- 为少数容易误识别的容器设置排除规则；
- 为关键页面声明少量明确邻接关系，例如“左侧列表 -> 右侧详情”；
- 为某些控件指定确定动作，避免只能坐标点击；
- 页面版本不匹配时自动退回通用算法，而不是执行旧坐标。

这类配置应只修正通用导航的已知缺口。若一个软件原生支持良好的 `Tab / Shift+Tab /
方向键 / Enter / Esc`，优先直接使用它自己的键盘导航，通常比 UIA 模拟更稳定。

## 10. 首轮验证清单

正式开发前，先用 A 档对实际目标软件做一轮短测试。每个软件只记录：

1. 首页或主窗口能找到多少真正可操作元素；
2. 关键按钮、输入框、列表项是否出现；
3. 是否有大量重复标签或整块容器噪声；
4. 普通确定是否正确，是否经常移动真实鼠标；
5. 打开弹窗、切换页面、滚动后重新触发是否正常；
6. 普通权限和管理员权限窗口是否有差异；
7. 首次触发和再次触发的等待时间；
8. RC003 注入的 leader 快捷键与提示字母是否都能被 Keyhop 接收。

结果分三类即可：

- **可直接用**：关键元素完整，噪声少，动作可靠；
- **可适配**：少量元素漏识别、重复或导航顺序问题，有稳定 UIA 特征可修；
- **不适合 UIA**：界面整体是自绘画面、远程画面或无障碍树不可用，应回到鼠标模式、
  软件原生快捷键或专用接口。

## 11. 建议决策

当前不应直接把 VibePad 合并进 Remote Mic，也不应马上开发完整空间导航。最合理的
下一步是：

1. 用 Keyhop v0.5.0 做一次外部工具实测；
2. Keyhop 提示字母固定为 8 个纯字母 `asdfghjk`；
3. 用 RC003 现有组合层输入这些字母；
4. 先测真正要控制的固定软件，而不是泛测整个 Windows；
5. 覆盖率通过后，再决定做 B 档 IPC 还是直接进入 C 档方向导航。

这样能先用现成产品回答“元素识别到底够不够”，避免在最关键事实未知时投入一套新的
导航器。

## 12. 独立键盘原型

2026-08-27 已新增 `scripts/element_navigation_prototype.py`，先验证电视式方向导航本身，
不接 RC003，也不进入 Remote Mic 正式运行时、配置、安装包或候选构建。

原型采用 `uiautomation 2.0.29` 读取当前前台窗口，PySide6 绘制不抢焦点的蓝色选中框，
低层键盘钩子只在导航期间吞掉方向键、Enter 和 Esc。它是可整块删除的实验入口，不能
替代 Keyhop 的成熟过滤、Chromium 唤醒、缓存和动作兼容层；原型失败也不能直接证明
Keyhop 不可用。

首次实测 ChatGPT/Codex 桌面窗口时，未唤醒状态只访问 61 个 UIA 节点并得到 14 个候选，
主要是窗口外壳。向其 `Chrome_RenderWidgetHostHWND` 及子窗口发送 `WM_GETOBJECT`
（`UIA_ROOT_OBJECT_ID=-25`、`OBJID_CLIENT=-4`）后，左侧列表和正文控件开始可见。2026-08-27
进一步核实发现，左侧具体会话和底部输入区位于 UIA 第 25 至 32 层，因此原型把 Chromium
最低扫描深度提高到 32。当前 ChatGPT 窗口一次定向扫描访问 926 个节点，保留 60 个有效
元素，根层显示 43 个；输入框、添加文件、权限、模型/强度、发送、`custom` 和下载按钮均
已进入候选。该结果只证明当前 ChatGPT/Codex 窗口，不代表所有 Electron/Chromium 软件
都已通过。

本轮还确认，ChatGPT 会同时暴露“整个项目块”、具体文件夹、具体会话，以及大量仅供
辅助阅读的“跳转到用户消息 N”小按钮。原型现按以下规则稳定候选：

- 同一位置优先保留有直接动作、可聚焦且层级更深的真实控件；
- 项目列表外壳包含具体文件夹或会话时，丢弃外壳而保留单条；
- 普通按钮内部的悬浮归档、固定等次级动作不与主按钮同时出现；
- 过滤“跳转到用户消息 N”辅助按钮和只有 Legacy 语义的无名结构块；
- 宽度足够且旁边存在列表的展开按钮视为文件夹入口，小型菜单按钮不误判为文件夹。

原型启动时优先选中鼠标所在位置下最小的可操作元素，鼠标位于窗口空白处时选择最近
元素。文件夹和当前可见子项现保持在同一个扁平导航面：展开中的文件夹可直接按方向键
进入首个子项，不再要求先按 `Enter` 进入内部导航层；`Enter` 只负责展开或收起文件夹，
`Esc` 直接退出导航。普通叶子元素执行后仍按当前原型规则退出，是否改成执行后重扫并
保持导航留待本轮人工手感确认。
方向移动现先判断目标是否与当前元素处于同一视觉横行或竖列，再按主轴距离、侧向偏差和
重叠程度比较；UIA 路径只提供有上限的区域亲缘加分，不能再让远处同分支元素压过近处目标。
左右方向仍支持电视网格式换行，但只允许进入相邻视觉行，不跨过大段空白跳到远处区域。
每个稳定布局使用按需生成的四向导航图，首次计算后直接复用邻居，并在自然成立时缓存反向
关系；规则网格自动测试覆盖全图可达和上下左右返回。
分组识别只把位于真实 `ListItem` / `TreeItem` 内部、带子列表的展开项当作文件夹；“项目”
和“最近”这类栏目标题不当成文件夹。分组信息只用于识别展开项，不再裁剪方向导航候选，
因此文件夹、可见子项、左侧栏和主内容区可以互相直接移动。

进入导航时现先用 UIA `ElementFromPoint` 命中鼠标所在元素，失败后最多等待 80 ms 做
MSAA 回退，并保留同一点的可操作祖先链；`PageUp` / `PageDown` 可在父子元素间切换。
窗口只移动位置时，每 250 ms 同步缓存坐标；尺寸或 DPI 变化时重新扫描。同步还抽查当前、
首部、中部和尾部元素：页面滚动或重新排版造成坐标变化时立即暂停导航，切换到其它前台窗口
也立即暂停，避免继续使用旧坐标。方向移动和执行前还会重新核对元素是否真实暴露，空白区域
中命不中的幽灵元素会被跳过。对于“已查看图片”
“已运行命令”这类面积较大、文字只在左侧的稀疏按钮，不再只检查矩形中心，而会检查中心、
左侧文字区和边缘多个点；任一点能通过 UIA 子元素及祖先链回到该按钮，就保留该按钮，并把
该点作为语义动作失败后的坐标点击兜底。此项自动测试已覆盖探测点和排序规则，真实展开、
收起效果仍为检查点待实测。

后续截图实测又暴露出两类边界。ChatGPT 的“复制”“复制消息”“从这里创建聊天分支”
会在未悬停时保持透明，但 UIA 仍提供有效矩形和 `Invoke`；原型现明确保留这些嵌套消息
动作，并允许有名称、有明确语义动作的标准控件跳过点命中校验，避免透明按钮被当成空白。
无名称 `GroupControl` / `PaneControl` 即使带内部 AutomationId，也不再进入候选，避免输入区
附近出现并不存在的按钮框。方向排序除视觉行列外还比较 UIA 路径公共前缀：同一主内容
分支优先于更近的侧栏项；横向换行还要求明显的左右回绕距离，侧栏中只有几像素缩进的
下一行不会再被误判为网格换行。以上规则已加入定向自动测试，真实 1–5 路径仍待人工复测。

随后实测发现，原有“进入文件夹子层”会把左侧栏和主内容区从候选列表中移除，导致主区
文件行按左无法回到侧栏；展开文件夹也必须先按 `Enter` 才能到首个子项，退出子层时还会
出现短暂卡顿。原型现已删除运行时子层级栈，所有当前可见目标始终使用同一候选列表；
定向测试覆盖“文件行按左到侧栏”和“展开文件夹按下到首个子项”，真实路径仍待人工复测。

2026-08-27 的性能复核还发现，普通 `Enter` 会先做多点 UIA 命中检查，展开/收起后会整窗
重扫，扫描期间定时同步和方向键还可能继续排队。原型现改为：有明确语义动作的按钮直接执行，
只有坐标点击兜底才做多点命中；展开项优先只刷新其父分支，失败才整窗重扫；同步、确定、
父子切换和方向移动设置待处理上限，退出导航后旧命令失效。300 个合成元素的四向首次邻居
计算约 4.2 ms，缓存后的 4000 次查询低于 1 ms；真实软件中的最终手感仍为检查点待实测。

随后真实日志确认两处性能与状态问题：`Ctrl+Alt+N` 冷扫描仍需约 2.3 至 2.5 秒；收起
文件夹虽已使用分支刷新，约 0.52 秒后仍因分支外元素随布局移动而被位置监控判定失效，
覆盖层窗口偶尔也会被误判成切换了前台软件。原型现先过滤无关 UIA 节点，并把同一控件
重复的动作模式查询合并为按常用顺序的单次探测；当前 ChatGPT 窗口冷扫描降到约 1.1 至
1.2 秒。导航未启用时会后台预识别稳定的前台窗口，15 秒内布局锚点未变时，热键直接复用
缓存。文件夹展开或收起后除刷新所在分支，还会快速同步全部已有候选的新矩形并丢弃已离屏
控件；前台监控明确忽略原型自己的覆盖层进程。后台预识别与自动检查已通过，热键体感和
文件夹离开路径仍为检查点待实测。

首次启动新版原型时，热键和扫描实际已经工作，但混合缩放环境中看不到蓝框。核实发现
当前两块屏幕分别为 150% 和 100% 缩放，`uiautomation` 先于 Qt 导入时会抢先设置旧式
系统 DPI 感知，导致 Qt 覆盖层被缩小并把底部目标画到窗口外。原型现于导入 UIA 前设置
Per-Monitor V2，并改为按目标所在显示器单独覆盖、按该屏缩放换算 UIA 物理坐标。修正后
已通过全屏截图确认蓝框实际显示在 ChatGPT 目标元素上；不同缩放屏之间移动仍列为人工
实测项。

在 `apps/windows/rc003` 下运行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r scripts\requirements-element-navigation.txt
.\.venv\Scripts\python.exe scripts\element_navigation_prototype.py
```

键盘操作：

- `Ctrl+Alt+N`：扫描当前前台窗口并进入导航；再次按下退出；
- 方向键：移动蓝色焦点框；
- `PageUp` / `PageDown`：在鼠标点或当前元素的父子层级间切换；
- `Enter`：展开/收起文件夹，或执行普通元素；
- `Esc`：退出导航；
- `Ctrl+Alt+Q`：关闭原型。

也可只扫描当前窗口并在控制台列出元素，不安装全局键盘钩子：

```powershell
.\.venv\Scripts\python.exe scripts\element_navigation_prototype.py --scan-only
```

退出条件：目标固定软件的 UIA 覆盖率完成实测后，这个 Python 原型不继续扩成正式产品；
正式接入仍按本文结论，优先采用 Keyhop 元素底座和本地 IPC。

## 13. PixPin 与 yuSnip 补充深挖

### 13.1 PixPin 真正证明了什么

PixPin 官方文档明确提供三档 UI 检测：“检测元素”“仅窗口”“不检测”。进入截图后，
鼠标停在目标位置会自动高亮元素或窗口，还可以用滚轮在同一点的父子元素之间切换。
这说明截图工具的成熟交互不是把全屏矩形一次性摊平，而是同时保留“当前点”和“祖先链”。

但 PixPin 也明确说明：元素识别依赖目标软件提供的系统 UI 辅助接口；软件不提供接口或
主动屏蔽时，只能退回窗口范围，不能继续识别内部按钮和文本框。因此不能把 PixPin 的
OCR 或图像模型理解成“任何图标都能自动变成可点击按钮”。

2026-08-27 对本机安装做了只读核实：

- 版本为 `3.5.2.2`，安装路径为
  `%LOCALAPPDATA%\Programs\PixPin`；
- `UiSpy.dll` 和 `UiRegionDetector.dll` 中可见 `IUIAutomation`、`ElementFromPoint`、
  `IAccessible`、`AccessibleObjectFromWindow` 和 `WindowFromPoint`；
- 安装目录同时包含 `PixVision.dll`、`PixOCR.dll`、`PixOCR2.dll`、`onnxruntime.dll`、
  `detect.caffemodel` 和 `paragraph_recognition.onnx`。

这些证据只能证明 PixPin 整个产品同时拥有无障碍命中、窗口命中和视觉/OCR 模块，不能
证明视觉模块参与了普通 UI 元素框选。结合官方回退说明，当前应按“UIA/MSAA 识别元素，
Win32 识别窗口，视觉能力服务其它图像功能”理解，除非以后有更直接证据。

PixPin 没有公开任意元素枚举、父子遍历或执行按钮动作的外部接口。公开脚本目前能取得
活动窗口、鼠标所在屏幕和历史截图区域等矩形，但不能把内部 UI 元素对象交给 Remote Mic。
因此它适合作为产品交互和分层架构参考，不适合作为正式运行时依赖，也不应逆向调用私有
DLL。

本轮曾尝试用当前本机快捷键自动触发一次截图并在同一点发送滚轮，屏幕没有出现可确认的
截图高亮变化，因此没有把这次自动化尝试当作行为证据。父子切换能力仅按 PixPin 官方文档
记录，后续如需比较手感，应由用户在真实界面手动实测。

### 13.2 yuSnip 当前实现的调用链

2026-08-27 核实 yuSnip `main` 提交
`b929de962d971feb2ae726bac67f0fa6be8af5dd`。当前自动检测入口有三种用户可选模式：
“检测元素”“仅窗口”“不检测”；旧的 `Auto` 枚举实际会映射回“仅窗口”。

“检测元素”的真实顺序是：

1. 用 `IUIAutomation::ElementFromPoint` 获取鼠标点下元素及其矩形；
2. UIA 失败后，用 MSAA 的 `IAccessible.accHitTest` 和 `accLocation` 回退；
3. 单次元素调用超过 80 ms 就放弃等待，避免拖住截图界面；
4. 专用 STA 后台线程只处理最新鼠标点，旧点直接覆盖，最短检测间隔 20 ms；
5. 截图覆盖层临时设置为命中穿透，防止检测到自己的全屏窗口。

“仅窗口”则使用 `WindowFromPoint` 命中深层 HWND，再用 `GetAncestor(GA_ROOT)` 升到顶层，
优先读取 DWM 视觉边框，失败才回退普通窗口矩形；命中失败时使用提前缓存的顶层窗口
Z 序列表兜底。

yuSnip 当前没有实现 PixPin 式“滚轮切换父子元素”。截图尚未形成手动选区时，滚轮没有
接入自动检测层级；形成选区后，滚轮用于扩缩选区或调整标注参数。其自动检测结果也只有
一个 `Rectangle`，没有保留元素名称、控件类型、AutomationId、动作模式、父元素链或可
执行对象，所以不能直接承担电视式方向导航和确定操作。

另外，仓库根目录没有 `LICENSE`、`COPYING` 或其它明确许可文件，README 只写“遵循开源
软件协议”。在作者补充明确许可证前，可以研究公开行为和重新实现技术思路，但不能直接
复制源码进入 Remote Mic，也不能把其二进制作为正式依赖分发。

### 13.3 与现有原型的正确结合方式

PixPin、yuSnip 和当前原型解决的是不同问题，合理组合不是三选一：

1. **全树候选仍以现有 UIA 扫描为主。** 方向导航必须同时知道屏幕上多个可操作元素，
   还要保留名称、类型、动作和层级；单点截图命中无法替代这一步。
2. **增加 yuSnip 式单点命中作为入口。** 进入导航时先对当前鼠标点执行 UIA
   `ElementFromPoint`，失败再做 MSAA `accHitTest`，然后把命中对象映射到全树候选。
   这比“从所有候选中找包含鼠标点的最小矩形”更准确，也有机会找到深层小图标。
3. **保留 PixPin 式祖先链。** 单点命中后记录从叶子到窗口的可操作祖先，允许在同一点
   切换“图标按钮、消息块、对话区域、整个窗口”。正式按键如何映射需另行确认，不能
   直接照搬鼠标滚轮。
4. **Win32 只做窗口兜底。** UIA/MSAA 都失败时，至少定位鼠标下窗口；窗口内部不能
   凭空推断按钮，可退回软件原生键盘导航、普通鼠标模式或专用应用规则。
5. **视觉/OCR 只作为低置信度补救。** 它可以提出“看起来像按钮或文字块”的矩形，但
   没有按钮语义和可靠动作。若未来确需加入，应单独标记为坐标点击候选，并按固定软件
   建立白名单，不能与可执行 UIA 元素混为一类。

建议的正式检测层因此调整为：

```text
全树 UIA 候选与语义动作
  + 当前点 UIA ElementFromPoint
  + MSAA accHitTest 回退
  + Win32 窗口回退
  + 固定软件规则
  + 可选的低置信度视觉/OCR 坐标候选
```

这条路径能直接回应当前实测问题：方向导航继续使用全局候选；启动时更准确地落在鼠标
所在小元素；父子层级不再只靠原型对列表结构的猜测；UIA 树漏掉但 MSAA 暴露的旧式控件
还有一次补救机会。对完全自绘且不暴露无障碍信息的图标，PixPin 和 yuSnip 也没有现成的
“识别后可靠执行”能力，仍需专用规则或视觉坐标方案。

## 14. 原型完整检查与应用阶段判断

本轮把原型按“固定软件中的电视式元素导航”完整推演了一次，并修正以下真实问题：

- 连续按同一方向在重叠、错位元素中可能绕回已访问位置；现在同一方向不会重复访问，
  改变方向后仍能返回，立即按相反方向时优先回到刚离开的元素；
- 后台预识别原先每 15 秒重复扫描前台窗口，真实日志中曾出现约 38 秒的扫描并阻塞
  `Ctrl+Alt+N`；现在只在窗口稳定后预识别一次，预算为 1.5 秒，主动扫描可以取消预识别；
- 前台窗口句柄短暂无结果会使监控回调异常退出；相同名称但不同位置的元素可能被错误
  合并；文件夹刷新可能在第一次数量变化后过早结束；以上均已增加失败保护和回归测试；
- 命令行扫描遇到控制台编码无法表示的字符时会中断；现在标准输出统一为 UTF-8；
- ChatGPT 的“展开显示”已在真实 UIA 树中确认是启用、可聚焦且支持 `Invoke` 的
  `ButtonControl`。此前实测使用的后台进程早于对应修复启动，重启后已加载新规则。

自动推演覆盖 800 组随机不规则布局、85,375 次连续同方向移动和 124,000 次立即反向，
结果为零循环、零反向丢失。300 个元素的全部 1,200 个首轮方向候选计算约 0.58 秒，缓存后
120,000 次查询约 0.03 秒；正常使用只按需计算当前元素的一个方向，因此方向键本身不是
性能瓶颈。运行态复核确认：同一稳定窗口不再周期性重复预识别，热键扫描任务栏约 0.15 秒，
ChatGPT 预识别约 1.0 至 1.4 秒，错误日志为空。

结论是：原型已经达到**受控应用试用阶段**，但尚不能作为默认正式功能或候选发布。下一步
应把它做成默认关闭的独立伴随进程，由桥接通过本地 IPC 发送“进入、方向、确定、返回”命令；
UIA 扫描不能进入 BLE、HID 或语音线程。首批只对白名单固定软件启用，窗口切换、扫描超时和
坐标失效均失败关闭，这样即使某个应用的无障碍树很慢，也不会拖住遥控器和语音主链路。

在 2026-08-27 完整检查结束时，正式接入前仍待确认以下交互：

1. 普通按钮执行后退出导航，还是重新扫描并继续停留；
2. 新弹窗或新窗口出现时自动跟随，还是暂停后由用户重新进入；
3. UIA 语义动作失败后的坐标点击是否允许移动真实鼠标，以及点击后是否恢复原位置；
4. RC003 使用哪个组合主键，返回键在导航中固定退出还是承担其它返回语义；
5. 音量键在导航模式中是否仍调音量，还是改为页面滚动。

这些问题当时只允许继续使用键盘原型验证，不能写入正式配置合同、运行依赖或候选包；
2026-08-28 已确认的结论见下一节。

## 15. 2026-08-28 单一元素操作模式

本轮明确不再增加自由鼠标模式、拖拽、OCR 或视觉识别。遥控器只需要进入一个元素导航
状态，方向键移动蓝框，确定键执行真实左击；快速按两次确定键会在同一验证坐标发送两次
Windows 鼠标点击，由系统按自己的双击时间识别为原生双击。菜单键在蓝框位置右击，音量
加减在蓝框位置上下滚动，返回键退出；`PageUp` / `PageDown` 继续保留同一点父子元素切换。

执行顺序也统一为一条：UIA 元素先通过当前屏幕点命中验证，再发送真实鼠标事件；MSAA
回退元素使用其真实命中矩形中心；只有元素确实暴露语义动作、但无法取得可靠坐标时才回退
UIA 语义执行。右键不对仅有语义、实际无法命中的隐藏控件伪造坐标。快速第二次左击复用
首击刚验证的坐标，避免再次扫描拖过 Windows 双击时限；连续滚动短时间复用同一屏幕点，
停止滚动后才重扫页面，避免每个音量键重复都触发 UIA 全树扫描。

右键后的菜单分两类处理：Windows 原生菜单打开时，方向、确定和返回暂时交还给系统菜单，
菜单关闭后自动恢复蓝框导航；网页或应用自绘菜单仍在原窗口内，右击后延迟 120 毫秒重扫，
把新出现的菜单项加入候选。双击后延迟 180 毫秒重扫，文件夹或页面切换后继续保留导航，
不再因内容滚动、重新排版或回车执行而直接退出。前台切到同进程窗口或当前窗口拥有的
弹窗时自动扫描并跟随，弹窗关闭后回到原窗口；切到无关软件时暂停退出。

自动检查新增并保留 65 项元素导航测试。随机推演覆盖 800 组不规则布局、734,471 次连续
同方向移动和 134,019 次立即反向，未出现循环或反向丢失。300 元素的 1,200 个首轮方向
查询约 0.57 秒，缓存后 120,000 次约 0.025 秒；500,000 轮按键映射、滚轮数据和窗口关系
判断约 0.17 秒，说明新增输入判断不是性能瓶颈。最终完整 unittest 1,450 项通过、7 项按
平台或安全条件跳过；公开边界扫描 341 个文件，`compileall`、`pip check` 和
`git diff --check` 通过。

当前结论是原型已经具备进入 RC003 应用接入阶段的元素操作闭环，但本轮仍只是独立键盘
伴随原型，没有接入正式按键出口、配置、依赖或冻结包。正式接入前只剩两项产品选择需要
确认：用哪个遥控器动作进入/退出元素导航，以及首批启用哪些固定软件。完全不暴露
UIA/MSAA 的自绘控件仍无法可靠识别；拖拽和任意坐标移动明确不在本模式范围内。

## 16. 2026-08-28 空间路径算法二次校正

本轮针对两个实测反例重新核对成熟空间导航实现，不再继续凭截图调整距离权重：

- W3C CSS Spatial Navigation Level 1 先筛选请求方向内的候选，再按主轴距离、正交轴
  距离、重叠和对齐度选优；规范本身没有把“从下一行左端绕回”置于正常方向候选之前。
- Android `FocusFinder` 使用 `isCandidate`、`beamBeats` 和主轴/次轴加权距离；同一条
  方向通道里的候选优先，方向外元素不能因为更近就抢走焦点。
- Chromium `spatial_navigation.cc` 明确处理矩形包含和重叠：离开子元素时跳过包住当前
  元素的底层容器，当前大块内部独立可操作的子元素则优先于外部下一项。

官方入口：

- `https://www.w3.org/TR/css-nav-1/`
- `https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/view/FocusFinder.java`
- `https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/page/spatial_navigation.cc`

原型据此保留已有四向距离和视觉通道规则，只修正两处通用边界：

1. 请求方向内已有正常候选时，默认先走正常候选；跨行绕回只作为网格末端补充。只有
   UIA 路径明确表明绕回仍在更近的同一内容分支时，才允许它先于斜向的其它分支候选。
2. 父块内部、纵向位置明显独立的小操作保留并优先，例如文件夹下方的“展开显示”；
   与父行重合的隐藏悬停按钮仍过滤，避免重新产生空白区域和侧栏假元素。

这不是照搬网页或 Android 源码，而是使用其候选边界和包含关系原则修正 Windows
UIA 原型。截图回归、真实 Codex 窗口扫描、随机布局和完整测试结果登记在
`TESTING.md` 的 `CHECK-NAV-003`。

## 17. 2026-08-28 改后横向对照

本轮在修正代码后继续核对 Windows、Qt 和电视端开源实现，目的是确认当前路径没有
围绕 Codex 截图形成一套只对单一窗口有效的规则。

### 17.1 成熟实现的共同结构

Microsoft WinUI 的 XY Focus 没有只提供一个固定公式，而是提供三种策略：边缘投影、
靠近方向轴、主轴与次轴曼哈顿距离；同时允许界面对四个方向显式指定目标。没有方向候选
时默认停在原处，不做全局循环：

- `https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.input.xyfocusnavigationstrategy`
- `https://learn.microsoft.com/en-us/windows/apps/develop/input/gamepad-and-remote-interactions`

Norigin Spatial Navigation 是面向 Tizen、webOS、电视盒子和 React Native TV 的生产库。
它先要求候选的前缘越过当前元素的后缘，再比较主轴和次轴距离；与当前元素在正交轴上
相邻重叠的候选会得到更低次轴权重。它还允许按布局选择角点、边缘或中心距离，提供按键
重复节流、可视化调试和容器级 `nextFocusResolver`：

- `https://github.com/NoriginMedia/Norigin-Spatial-Navigation`
- `https://devportal.noriginmedia.com/docs/Norigin-Spatial-Navigation/guides/distance-calculation`
- `https://devportal.noriginmedia.com/docs/Norigin-Spatial-Navigation/api-reference/SpatialNavigation/`

`js-spatial-navigation` 把元素分成显式 section，默认同 section 优先；还能设置直线重叠
阈值、记住来源、重新进入区域时回到上次焦点，并用 `leaveFor` 或四方向属性覆盖特殊路径。
隐藏或禁用元素会被过滤：

- `https://github.com/luke-chang/js-spatial-navigation`

Qt Quick `KeyNavigation` 则代表另一端：不猜距离，直接声明上下左右目标；它会自动补反向
关系，并跳过不可见或禁用项：

- `https://doc.qt.io/qt-6/qml-qtquick-keynavigation.html`

### 17.2 当前原型与它们的关系

当前原型已经具备成熟实现共有的底层能力：先限制请求方向，再优先视觉通道和正交轴重叠，
比较距离；移动前检查 UIA 元素仍启用、可见和可命中；同方向连续移动防重复，立即反向优先
回到刚离开的元素；稳定布局缓存四向结果，按键队列限制重复任务。

仍有三点差异：

1. 原型的“跨行绕回”是为本项目实测网格增加的补充，不是 Windows、W3C 或 Norigin 的
   通用默认。现在它只在正常方向候选不足且 UIA 路径显示同分支更近时优先，边界合理。
2. 成熟库由界面作者明确提供 section/container；跨软件 UIA 原型只能从控件树和路径推断。
   原始 UIA path 会随动态页面重排，因此只能作为辅助，不能继续提高到压过明显空间目标。
3. 成熟库普遍允许固定界面覆盖特殊方向，并提供候选路径调试图。原型目前只有蓝框和控制台
   结果，遇到新反例时仍要靠额外扫描还原每个候选为什么胜出。

### 17.3 建议

当前不需要替换距离算法，也不建议直接引入上述库。它们运行在自己拥有的 DOM、React、
XAML 或 QML 元素树中，不能直接控制其它 Windows 软件的 UIA 元素；强行接入只会增加一层
坐标转换和状态同步。

进入正式 RC003 接入前，建议按以下顺序继续：

1. 先增加可选的导航诊断输出，记录当前元素、候选方向、通道重叠、距离、容器亲和度和最终
   胜者；只在诊断模式启用，不增加日常按键开销。
2. 把“同区域”从单纯 path 前缀升级为语义容器：优先识别最近的 List、Tree、Tab、菜单、
   对话框和主内容 Pane，path 只作回退。这更接近成熟库的 section。
3. 只有固定软件连续出现无法由通用规则解决的真实路径时，再增加可选的软件级四方向覆盖；
   不提前维护大量坐标规则，也不把截图编号写进正式逻辑。

因此，改后复核没有发现必须立即推翻的算法问题。当前版本可以继续实测；下一项值得做的是
“可解释的候选诊断”，不是继续微调权重、增加自由鼠标模式或引入另一套运行时。

## 18. 2026-08-28 可选导航诊断

原型已加入默认关闭的候选诊断。运行时按 `Ctrl+Alt+D` 可以开关，也可以使用
`--diagnostics` 启动参数直接开启；不需要退出当前导航或重新扫描窗口。

开启后，每次按方向键都会在原型控制台输出：

- 当前元素、请求方向和最终移动结果；
- 实际候选顺序，以及候选属于同一通道、斜向候选还是跨行补充；
- 向前距离、横向偏离、综合值和 UIA 路径共同层级；
- 候选是否因本轮历史去重、此前失效或当前无法命中而被跳过；
- 其余元素未进入候选的原因汇总，包括方向不符、底层容器、同矩形和横向侧别过滤。

输出只显示前八个优先候选；实际排序和检查仍覆盖全部元素，若最终选中的元素不在前八个，
会额外显示该项。诊断只写当前控制台，不自动保存文件；元素名称可能来自当前软件界面，
需要保留日志时由使用者明确重定向输出。

关闭诊断时，方向移动只多一次布尔判断。开启诊断后，300 个模拟元素、158 个方向候选的
单次完整解释生成和格式化平均约 0.83 毫秒；控制台实际写出速度仍取决于宿主，因此诊断
只用于短时复现，不建议在开启时长期按住方向键。该能力用于判断下一步该修距离、区域、
命中检查还是固定软件路径，不改变现有候选排序本身。

## 19. 2026-08-28 主内容区横向互达

### 19.1 反例与根因

本轮实测中，主内容区左侧消息的“复制”和右侧消息的“复制消息”看起来应当通过左右键
直接互达，但从右侧按左会先跳到窗口左侧的对话列表。2026-08-28 只读检查真实 UIA 树：

- 左侧消息操作矩形为 `(1104,688)-(1143,727)`；
- 右侧消息操作矩形为 `(2170,875)-(2209,914)`；
- 两者 UIA 路径约有 26 层共同前缀，位于 `(934,242)-(2390,1759)` 主内容区；
- 抢焦点的对话项矩形为 `(509,891)-(899,937)`，在约第 13 层已经进入
  `(497,242)-(934,1759)` 左侧栏。

旧算法先比较视觉通道。侧栏对话项与右侧按钮纵向重叠，因此被判为最高优先级；同一
主内容区的左侧按钮因为高约 187 像素，只能进入斜向候选。原有 UIA 路径加分最多只看
四层，而且排在通道之后，无法纠正这个结果。问题不在左右方向识别，也不能靠继续放大
路径权重解决，否则固定界面中一个很远的同分支元素会压过近处的正常目标。

### 19.2 对照与实现

W3C CSS Spatial Navigation 使用 navigation container 限定候选上下文，并允许容器
控制焦点是否跨出；`js-spatial-navigation`、Norigin 和 WinUI XY Focus 也都允许以
section、容器或显式方向关系补充纯距离算法。跨软件原型不能取得界面作者声明的容器，
因此本轮从 UIA 祖先矩形推断窗口内第一个宽度明显小于整窗、但仍足够大的区域；
全宽的顶部或底部内容带不会被误当成左右分栏：

- `https://www.w3.org/TR/css-nav-1/`
- `https://github.com/luke-chang/js-spatial-navigation`
- `https://github.com/NoriginMedia/Norigin-Spatial-Navigation`
- `https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.input.xyfocusnavigationstrategy`

横向移动仍先生成原有同通道、斜向和跨行候选。只有同时满足以下条件，才把同区斜向
候选提到另一窗格的同通道候选之前：当前元素有可确认区域；最优同通道候选属于另一
区域；同区候选 UIA 路径共同层级更多；其纵向偏移和向前距离仍在按控件尺寸自适应的
有限范围内。另一窗格明显更近时不触发该规则，因此这不是强制锁区。

区域路径在扫描 UIA 树时一次生成，目标排序只比较短元组。扫描同时复用已经读取的控件
矩形，不对可点击控件重复查询位置。诊断模式会把该路径标为“同区优先”，以后出现反例
时可以直接区分区域选择与普通距离选择。

### 19.3 边界与验证

这项规则不写死 ChatGPT、Codex、按钮名称或截图坐标，也不假设每个窗口只有一种布局；
没有明显分区的普通窗口继续使用原空间排序。UIA 未暴露稳定祖先矩形时区域为空，功能
自动退回旧规则，不伪造容器。

元素导航 75 项自动测试通过，覆盖真实分栏几何、左右双向互达、诊断原因和另一窗格
明显更近时仍可跨出。800 组带随机区域的不规则布局连续移动 48,751 次，没有循环；
300 个元素的 1,200 个方向关系冷计算约 0.65 秒，平均约 0.54 毫秒。源码已达到重启
原型后继续实测的条件，真实窗口移动后的 UIA 更新和实际左右手感仍由人工确认。

## 20. 2026-08-28 网格坐标与区域出口修正

### 20.1 上一版为什么仍然错误

上一版只解决了“右侧消息操作按左被侧栏同通道抢走”，但把区域识别成第一个宽度
明显缩小的大祖先。真实 ChatGPT UIA 树中，顶部标题和正文滚动区共同位于右侧主列，
因此仍被归入同一区域。旧横向斜向规则还带有阅读顺序偏置：按右只保留下方斜向候选，
按左只保留上方斜向候选。结果是正文左边已经没有同区按钮时，按左会先去左上方标题，
再继续移动才可能进入侧栏。这与遥控器的二维方向直觉相反。

### 20.2 成熟实现给出的边界

Windows 把这类操作定义为二维 directional area。`Projection` 会沿请求方向投影当前
元素边缘，`NavigationDirectionDistance` 优先选择最靠近方向轴线的目标；方向轴附近
没有候选时才扩大，而不是把“先上后左”的阅读顺序塞进左键。W3C CSS Spatial
Navigation 先在当前 navigation container 中找请求方向候选，没有时再从容器边界
寻找外部目标。`js-spatial-navigation` 的 `restrict: self-first` 也是先查当前 section，
没有才退出，同时允许 `leaveFor` 明确容器出口：

- `https://learn.microsoft.com/en-us/windows/apps/develop/input/focus-navigation`
- `https://www.w3.org/TR/css-nav-1/`
- `https://github.com/luke-chang/js-spatial-navigation`

这些实现共同说明两层职责不能混在一个总分里：先判断当前属于哪个二维区域、是否要
离开；进入目标区域后，再按方向轴线和距离选择具体格子。

### 20.3 当前实现

跨软件 UIA 没有界面作者提供的显式 directional area，因此原型按以下顺序推断：

1. 优先采用最近的 `ListControl`、`TreeControl`、`MenuControl`、`TabControl`、
   `ToolBarControl`、`DataGridControl` 或 `TableControl` 语义祖先；
2. 没有语义容器时，识别占窗口主要高度的正文区，以及靠近窗口顶部、横向较宽的标题带；
3. 同时保存区域路径和矩形，窗口移动时两者对应的坐标一起平移。

横向移动分成两层：先把真实位于请求方向的候选按方向轴线贴合程度和二维距离排序，
上方、下方一视同仁；再用区域矩形排除顶部横带等非相邻区域。同区目标只有横向更近
且纵向偏移不过大时才保留直接互达，否则进入位于请求方向、与当前区域纵向相交且横向
最近的区域。跨行绕回只排在全部真实方向候选之后，不能再用“左上 / 右下”的阅读
顺序覆盖网格坐标。

这不是为 ChatGPT 写死坐标。固定界面只要 UIA 能提供列表、树或稳定祖先矩形，就按同一
规则形成二维区域；没有可靠区域时退回纯几何排序。自动检查覆盖 81 项定向测试、
800 组三分区随机网格的 71,289 次连续移动和 300 元素性能检查，未出现循环；1,200
个冷方向关系中位约 0.97 秒，单个关系平均约 0.81 毫秒。真实截图路径仍需加载新进程
后人工确认。

## 21. 2026-08-28 互动点优先与动态界面闭环

### 21.1 最终识别原则

元素导航的目标是接近鼠标点击能力，不是复刻截图工具的边界识别。候选只保留 UIA/MSAA
能够证明真实可操作的元素；只有焦点能力、但尺寸很大的布局容器不再进入候选。没有文字、
但具有实际操作模式的紧凑按钮仍保留，避免漏掉消息下方只显示图标的操作。

父块和子按钮都有独立动作时两者都保留。子按钮只在距离近、方向合理时优先，远处或明显
偏离方向轴的子按钮不能压过眼前父块。点击父块时，会从中心、两侧和四角候选点中排除
被已保留子按钮占用的位置；UIA 路径已经确认父子关系时，不再受面积接近或 1 像素边界
误差影响。这样既能点整行、整卡片，也不会误点其内部删除、复制或更多按钮。

### 21.2 四向自由移动

每次方向键仍先使用真实位于请求方向的空间候选，并按网格位置、方向轴贴合和局部区域
排序。只有这些正常候选已经走完，才进入覆盖全部剩余互动点的视觉顺序；同方向移动记录
已经访问的目标，直到所有目标都可达，不会在少数元素之间循环。反向返回由本次真实移动
历史处理，不再向缓存图中写入会受查询先后影响的反向边。

父子优先规则应用在最终候选顺序上，因此旋转到任意起点后，未访问的子按钮仍先于其
大父块；同时它只影响自身 UIA 后代，不会因为矩形重叠而误管另一分支。区域仍来自语义
容器和几何位置，没有按窗口名称硬编码模式，普通列表、工具栏、对话框和多栏界面共用
同一套规则。

### 21.3 动态页面与性能

原型通过 Windows `SetWinEventHook` 监听当前目标窗口的创建、销毁、显示、隐藏、重排和
状态变化。回调只标记变化，不读取 UIA 树；方向键遇到绕回、远距离或斜向等可疑移动时，
等待约 150 毫秒让连续事件合并，再刷新一次；等待期间又有事件也不会吞掉本次方向键。
若供应器漏报事件，缓存超过 5 秒后遇到同类可疑移动会刷新，超过 30 秒后的首次移动则
无条件刷新。扫描只消费开始前已经存在的变化代数，扫描期间的新变化会保留；预识别取消
或失败时恢复原监听窗口，不能继续复用另一窗口的旧缓存。两个事件范围必须全部安装成功，
否则明确进入缓存时限兜底。

最终源码的元素导航定向测试共 99 项通过。额外随机推演覆盖 500 组界面、272,832 次连续
四向移动，零循环、零提前停止、零漏达；100 组随机查询顺序与固定顺序结果一致。300 个
元素的冷查询平均约 0.77 毫秒，P95 约 1.24 毫秒。完整 unittest 共 1,492 项通过、7 项按
平台条件跳过，公开边界扫描 348 个文件通过，`py_compile` 与 `git diff --check` 通过。

因此源码已经达到受控应用试用条件，不需要增加自由鼠标、OCR 或截图式大范围边界识别。
当前仍在运行的旧原型不会自动加载这些修改；重启后还需在真实宿主窗口验证动态图标、
父子点击、长时间使用和 RC003 实体按键，状态为检查点待实测。

## 22. 2026-08-28 固定软件互动点补全

### 22.1 为什么仍要补三种识别来源

单靠标准 UIA 动作不能覆盖本机三类真实界面：QQ 把会话和消息暴露成重复内容组，
但组本身没有标准点击动作；Quicker 的浮动动作属于另一个进程的顶层小窗口；
Directory Opus 的文件窗格只暴露整个旧式 Pane，不暴露其中的文件项。继续放宽大容器
会重新产生空白框和整窗框，因此本轮没有取消互动过滤，而是为这三类缺口增加受限来源。

### 22.2 当前实现边界

- Chromium / Electron 重复内容只在同一父容器下至少出现三行、尺寸相近、内部具有
  可见文字或图像时提升为坐标点击项。普通两块布局、超大内容块和离屏行不会进入。
- 跨进程悬浮窗只枚举主窗口上方、面积不超过主窗约 35%、自身至少约 65% 覆盖在主窗
  内的小窗口；同进程、所有者关系、Topmost、ToolWindow 或 NoActivate 只用于证明
  关联，任务栏和桌面类明确排除。悬浮窗出现、消失或抢到前台时刷新，但不退出导航。
- 视觉后备只用于可聚焦、带 Legacy IAccessible，且有表头或滚动能力的大型旧式窗格；
  若 UIA 已经覆盖足够多真实目标则不启用。截图只在该窗格内降采样到不超过 720 像素宽，
  识别规则文字行或缩略图格；多组连续文件行均保留，远处少量状态文字会被丢弃。

这不是通用 OCR，也不识别截图边界。视觉项没有按钮名称和语义动作，只提供当前前台窗格
内的坐标点击、右击和滚动；窗口移动时坐标同步平移，滚动后延迟刷新。正常 UIA 窗口仍走
原来的动作、命中校验和缓存路径。

### 22.3 实测与性能

2026-08-28 本机只读扫描结果：QQ 共得到 66 个可导航目标，包含会话行、消息块和输入区
图标，扫描约 1.21 秒；Directory Opus 共得到 33 个目标，其中左右文件窗格分别识别
15 行和 8 行，底部状态区不再生成大空白框，扫描约 0.44 秒。纯计算压力检查中，
4,000 个元素的重复内容归并平均约 2.72 毫秒，旧窗格筛选约 2.00 毫秒，720x450
视觉扫描约 84.29 毫秒；真实冷扫描主要时间仍来自宿主 UIA 枚举。

元素导航定向测试现为 127 项全部通过，覆盖重复行过滤、旧窗格启用条件、详情行与
缩略图网格、视觉离群分组、悬浮窗关系/面积/重叠、跨进程前台保持、指定窗口诊断扫描
和合成点击坐标平移。随后真实 Quicker `FloatButtonWindow` 出现，确认其 UIA 树只有窗口
根节点、没有子控件；原型现只对已经通过悬浮窗过滤、宽高均不超过 200 像素且内部没有
目标的小窗，把窗口根本身补为一个坐标格。指定 Codex 窗口只读扫描已得到 3 个
`OverlayWindowControl`，不再是 0 个。`py_compile` 与 `git diff --check` 通过。本轮不构建、
不打包、不发布；真实选中、回车调用、长时间运行和 RC003 实体按键仍为检查点待实测。

## 23. 2026-08-28 统一屏幕网格与 Quicker 状态辅助

### 23.1 当前结论

窗口、浮窗和视觉后备只是互动点的不同来源，不应该形成彼此独立的导航模式。识别完成后，
所有互动点都拍平成屏幕坐标上的同一组矩形；方向键只看请求方向、轴线贴合、前进距离和
局部几何关系。Quicker 的进程关联状态只回答“这个浮窗是否属于当前软件”，不能回答
“按右应该先去哪个元素”，因此不得进入方向评分。

此前动态单元格为保证从任意起点遍历全部目标，会给孤立格插入双向边，并在多个分区之间
强制补连接；区域路径还可能把同区目标提前。这能提高图论上的连通率，却会改写正常的
二维方向：屏幕右侧已有近邻时仍可能先去上方，或者为了接入某个孤立点让常用路线绕远。
这些路径现已退出运行。没有正常方向候选时停在边界，比悄悄替用户改变方向更符合遥控器
模拟鼠标的目标。

### 23.2 Quicker 状态合同

原型支持可选 JSON 快照，默认位置为
`%LOCALAPPDATA%\RemoteMic\RC003\quicker-navigation.json`，也可用
`--quicker-state-file` 或 `REMOTE_MIC_QUICKER_STATE_FILE` 指定。每项只需要窗口句柄、
是否绑定、绑定进程名和可见状态；明确绑定当前软件的浮窗即使位于主窗口外，也可以加入
统一网格。

本机 Quicker `1.45.5.0` 内部对象具备 `IsBindProcess`、`BindProcessName`、`ItemId`、
位置和尺寸，但公开 `IQuickerApi` 没有列出浮窗枚举接口，`quicker.db` 也不是可直接读取的
普通 SQLite。本轮因此只建立只读快照合同，没有修改用户 Quicker 配置，也没有安装导出
动作。快照不存在、损坏或暂时未更新时，当前可见且可信的小型 `FloatButtonWindow`
仍可按已有规则加入，功能不会因状态桥缺失而完全失效。

### 23.3 验证与边界

真实坐标回归覆盖窗口边缘动作、右侧最近 Quicker 浮窗和两个上方消息操作：按右先到
右侧最近浮窗，按左直接返回，不再被上方元素或区域关系抢走。元素导航 130 项全部通过；
300 个目标的网格初始化约 63.7 毫秒，首次计算全部 1,200 个方向约 499.8 毫秒，缓存后
120,000 次查询约 24.1 毫秒。`py_compile` 和 `git diff --check` 通过。

这证明算法和只读识别已达到继续应用试用的条件，但不替代真实操作验证。Quicker 状态导出
动作尚未制作；真实回车调用、窗口外关联动作、浮窗出现和消失后的长期稳定性，以及 RC003
实体按键仍为检查点待实测。本节取代第 21 节和 `CHECK-NAV-009` 中“插入孤立格、强制
连接分区”作为当前实现规则的结论，历史数字只保留为当时事实。
