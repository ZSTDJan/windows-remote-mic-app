# 无线麦 SayAll 与言灵 Vibe Flow 功能借鉴专项

日期：2026-08-27

状态：调研完成，实施未授权

范围：Windows RC003 的首次使用、语音验收、运行反馈、诊断、语音工具适配与后续产品能力

## 1. 文档目的与边界

本文比较两个公开项目当前能提供的用户能力，并结合 Windows RC003 现状判断：

- 哪些能力解决的是我们现在真实存在的问题；
- 哪些适合近期落地，应该放在哪个页面；
- 哪些虽然有吸引力，但会引入新的配置、权限、隐私、音频路由或发布风险；
- 哪些只应保留为研究方向，不应因为对方已经展示就直接照搬。

本文是 `2026-08-24-upstream-ui-and-feature-adoption.md` 的补充，不替代其中已经形成的
界面与测试通道结论。本文不修改配置 schema、运行时、界面或发布流程，也不代表候选
功能已经排期。后续实施仍按项目影响级别和交互变更规则单独确认。

## 3. 三个项目现在分别强在哪里

### 3.1 言灵 Vibe Flow

言灵与我们同为 Windows RC003 路线，最有价值的不是页面外观，而是把“能跑”推进到
“普通用户能配置、能确认、出问题能知道卡在哪里”：

- 五步首次使用向导，最后必须在应用内真实说一句并看到文字；
- 微信输入法、Typeless、Windows 语音输入、Voquill 和自定义工具的预设；
- 首页显示真实音频是否到达，而不是只显示桥接进程是否存活；
- 会话健康指标，包括音频覆盖率、包间隔、队列丢包、WASAPI、端点和恢复次数；
- 后台组件启动顺序、预热、丢失或卡住后的恢复；
- 脱敏问题摘要、诊断导出和一次性详细音频诊断；
- 连续听写、临时默认麦克风路由、更新校验和可选代码签名。

它目前明显领先我们的部分，是 Windows 用户可见的完整使用闭环，而不是 RC003 基础
协议本身。

### 3.2 无线麦 SayAll

无线麦的优势是产品范围和长期结构更完整：

- 全新安装向导以真实权限、遥控器、音频、普通按键和文字结果作为门禁；
- 测试音、使用统计、自定义 App、输入框定位、首选输入法准备；
- 单击、双击、长按、映射方案和组合动作；
- 本地文字回眸，以及按客户端独立授权、可撤销、只读的 MCP 访问；
- iPhone、Apple Watch 和网页遥控/收音；
- 正式/预发布更新中心、签名、公证和多架构发布。

但其中不少能力是 macOS 专属、候选待验收或依赖私有组件，不能据此判断 Windows 版
也已经有同等可复用实现。

### 3.3 我们当前 Windows RC003

以下能力已经存在，不应为了看起来接近对方而重做：

- RC003 BLE/ATVV、ADPCM 解码、指定端点输出和桥接监督；
- 13 个实体键检测和映射，单击、双击、长按及适用动作的按住重复；
- Raw Input、低层钩子和可选 Frida HID tap 的 Windows 专属按键补全；
- 设置与桥接进程分离、托盘入口、原子配置保存和热加载；
- 明确选择输出端点，不静默改 Windows 默认音频设备；
- 语音程序启动与权限状态、VB-CABLE 安装修复入口和本地通道测试；
- 较完整的自动检查、构建门禁和真机待测边界。

当前主要差距不是“缺少更多按钮动作”，而是用户还不能在一个清晰流程里证明：

1. 桥接真的收到 RC003 音频；
2. 音频真的送进虚拟麦克风；
3. 输入法真的开始识别；
4. 文字真的出现在目标输入框；
5. 失败时究竟卡在哪一层。

## 5. 第一优先级：补上真正的语音验收

### 5.1 当前“测试通道”到底测什么

现有“测试通道”发送约一秒合成信号，验证：

```text
CABLE Input -> VB-CABLE -> CABLE Output
```

它不需要用户说话，也不验证 RC003、宿主快捷键、输入法或文字上屏。这个功能有排障
价值，但名称容易让用户误以为是完整语音测试。

建议把名称改为更明确的“测试声音通道”，并继续保留在诊断页；主页可以提供同一
功能的次要快捷入口，但必须复用现有 `testVbCableChannel()`，不能复制第二套逻辑。

### 5.2 新增独立的“试说一句”

两边最值得直接借鉴的是：在应用自己的可编辑输入框内完成一次真实语音验收。

建议用户流程：

1. 在主页“语音输入”区域点击“试说一句”；
2. 页面展开一个测试输入框并自动聚焦；
3. 用户按住 RC003 话筒键，说一句固定或任意短句后松开；
4. 页面分别显示“收到遥控器音频”“已送入输出端点”“检测到文字变化”；
5. 文字出现后显示“本机语音链路已通过”；没有文字则指出下一步检查输入法、快捷键
   或 CABLE Output，而不是笼统显示失败。

这一方案不需要读取其它 App，不需要剪贴板监听，也不需要 Windows UI Automation。
程序只观察自己测试输入框的文字是否发生变化，因此权限、隐私和兼容范围都更可控。

### 5.3 主页建议布局

主页现有“输出端点”和“保存与启动”之间增加一个紧凑的“语音可用性”区域：

- 当前状态：未测试 / 等待遥控器 / 声音已到达 / 等待文字 / 已通过 / 需检查；
- 主操作：“试说一句”；
- 次操作：“测试声音通道”；
- 一行最近结果：时间、音频是否到达、文字是否出现；
- “查看详情”进入诊断页，不把完整技术指标堆到主页。

这样用户能在主页完成常用确认，诊断页仍负责驱动、端点、日志和详细指标。

## 6. 第二优先级：让状态说明真实可用程度

### 6.1 首页实时语音状态

言灵把“逻辑会话已经开始”和“真实音频正在到达”分开，这一点非常重要。我们的首页
目前更接近配置与进程状态，容易让用户把“桥接运行”理解成“语音已经可用”。

建议增加最小运行状态，不先做复杂图表：

- 正在等待 RC003；
- 已检测到话筒键；
- 已收到第一帧有效 PCM；
- 当前语音持续时间；
- 输出端点正在写入；
- 已松手并排空；
- 本次没有收到音频 / 输出失败 / 宿主快捷键失败。

这些状态必须由桥接运行事实产生，通过现有运行状态合同扩展给设置页，不能由 QML
自行计时或猜测。

### 6.2 最近一次会话健康摘要

建议先保存或发布一份很小的脱敏结果：

- 开始原因和结束原因；
- 是否收到有效音频；
- 持续时间；
- 最大音频包间隔；
- 解码或输出丢弃数量；
- 实际输出端点和 host API；
- 宿主快捷键是否完整按下、释放；
- 是否正常排空。

不记录 PCM、识别文字、窗口标题、蓝牙地址或完整设备路径。第一页只显示白话结论，
诊断页和导出摘要再显示技术字段。

### 6.3 脱敏问题摘要

建议在诊断页增加“复制问题摘要”，汇总版本、运行模式、设备/端点是否存在、桥接
阶段、最近会话健康和失败码。它比让用户自行寻找并发送整份日志更安全，也更容易
远程排查。

## 7. 第三优先级：语音工具预设与首次使用向导

### 7.1 语音工具预设

言灵为微信输入法、Typeless、Windows 语音输入、Voquill 和自定义工具维护不同的
快捷键、触发语义、启动等待和说明。这个方向值得借鉴，但不应直接复制其默认值。

Windows 第一阶段建议只做经过我们实际验证的少量预设：

- 豆包输入法；
- 微信输入法；
- Windows 语音输入；
- 其它自定义程序。

每个预设至少明确：程序如何查找、是否需要启动、快捷键是按住还是点按、输入设备
应选择什么、当前是否经过本项目真机验收。尚未验证的工具只提供“自定义”，不能
显示成官方支持。

当前正式语音生命周期只有“按住说话”。需要点按切换的宿主不能仅靠预设名称接入，
必须另行决定是否增加新的宿主触发语义，不能把它与 RC003 音频生命周期混为一谈。

### 7.2 首次使用向导

向导应复用正常页面和运行时的真实状态，不创建第二套“向导专用检测”。建议步骤：

1. 选择 RC003 与语音工具；
2. 检查或安装 VB-CABLE；
3. 识别真实遥控器和普通按键；
4. 核对语音快捷键并运行“测试声音通道”；
5. 在测试输入框完成“试说一句”。

只有第 5 步文字真实出现，才能说明本机端到端语音已经通过。允许用户退出向导，但
主页应持续显示未完成项；不要只保存一个“向导完成”布尔值掩盖后续设备变化。

## 8. 稳定性借鉴：先补证据，再自动恢复

言灵值得借鉴的稳定性做法包括：

- 后台捕获和按键桥分别有单实例与版本检查；
- 开机后等待捕获服务和语音工具真正准备完成；
- 组件丢失或卡住时恢复，并记录恢复原因；
- 音频、端点和会话都使用 generation 所有权，旧会话不能关闭新会话；
- 异常退出后通过本地恢复标记修复临时系统状态。

我们的桥接监督、资源清理和会话所有权已经有基础。近期应先把“哪个组件未准备、
首次按键为什么失败、恢复发生了几次”变成可见证据，再决定自动重启策略。没有准确
观测就增加自动恢复，可能把真实故障变成循环重启。

## 9. 重要但不能直接照搬的能力

### 9.1 连续听写

言灵 `v1.2.0` 公开实现的连续听写不是简单忽略松手，而是：物理流自然停止后由主机
重新打开音频流，按固定周期发送 `MIC_EXTEND`，监控真实音频覆盖和停顿，并在失败
时有界恢复。其文档记录了 124 秒、6 分钟和 15 分 22 秒的真机结果。

但无线麦公开档案明确写着普通物理遥控器的 `MIC_EXTEND` 延长方案已撤回；我们此前
的 On-request 专项探针也没有取得可作为正式路径的启动证据。因此，这里存在真实的
实现和环境差异，不能因言灵单机验证成功就直接恢复我们的旧开关路径。

建议把连续听写作为独立 L3 研究，至少满足以下门禁后才讨论进入产品：

- 在我们的 Python/WinRT/RC003 链路复现主机重开和精确关闭；
- 连续 2 分钟、6 分钟、15 分钟都有非零真实 PCM 和可见文字；
- 记录覆盖率、最大包间隔、续租成功率、输出丢弃和内存；
- 断连、休眠、快速再次开始和输入法失败都能收尾；
- 不复活已经结束的旧会话，不影响现有按住说话；
- 真机通过前只存在于独立实验入口，不进入正式配置 schema 和默认界面。

### 9.2 临时默认麦克风路由

言灵会在听写期间把 Windows 三类默认录音角色临时切换为 `CABLE Output`，完成后
恢复原设备，并使用 generation、回滚和崩溃恢复标记防止旧会话覆盖新状态。

它能减少用户在不同输入法中手动选择麦克风的成本，但与我们当前“不自动修改默认
音频设备”的公开边界直接冲突。实现错误可能影响会议、录音、游戏语音和远程软件。

建议当前不实现。只有真实用户反复遇到“目标输入法无法单独选择 CABLE Output”，
且用户明确接受每次听写临时切换时，才单独设计为默认关闭、可恢复、可审计的功能。

### 9.3 本地使用统计

无线麦按日、周、全部范围记录按键次数和语音时长。这对了解使用价值和发现按键失灵
有帮助，但会新增持久数据格式、保留周期、清空和损坏恢复。

建议先完成最近一次会话健康摘要；只有用户确实需要长期趋势时，再把统计作为独立
L3 数据功能，不与界面优化一起做。

### 9.4 任意 App、映射方案和组合动作

任意 App 选择比继续扩充固定名单更实用。第一版可以只允许用户选择本机 `.exe` 或
`.lnk`，支持“打开”或“激活”，不接受脚本、参数、命令行和网络路径。

多套映射、按前台 App 自动切换和组合动作会同时引入配置迁移、窗口识别、焦点、
动作取消、失败停止和竞态。它们应排在核心语音验收、真机稳定和任意 App 基础能力
之后。

### 9.5 文字回眸与 MCP

无线麦通过 macOS Accessibility 比较语音前后的安全文本快照，再默认关闭地保存
确认新增文字；MCP 只读层建立在这份可信历史上，并有客户端独立令牌、哈希保存、
撤销、文件权限和审计。

Windows 当前不拥有识别结果，也不能可靠读取任意输入框。若为此引入 UI Automation、
剪贴板监听或键盘记录，会显著扩大权限、隐私和兼容风险。当前只应借鉴它的原则：
默认关闭、最小数据、敏感输入拒绝、客户端独立授权和可撤销；不应先做空的 MCP
入口或为了回眸读取所有输入内容。

### 9.6 手机、Watch 和网页接力

这些能力需要独立客户端、配对协议、身份和信任、局域网或蓝牙传输、音频分包和
跨设备恢复。它们属于新的产品线，不是 Windows RC003 近期补齐基本体验的低成本
功能，当前不进入主线。

### 9.7 自动更新

言灵已经实现 GitHub Release、HTTPS 资产和 SHA-256 校验；无线麦还有 Sparkle、
签名、公证和正式/预发布通道。我们当前仍是未签名候选，更新来源、签名、回退和
防降级合同尚未稳定。应先稳定签名与发布，再增加用户确认的更新入口，不能先做一个
看起来“自动更新”但缺少可信发布链的按钮。

## 10. 推荐实施顺序

### 阶段 A：语音可用性闭环

用户结果：不离开主页就能分清“通道通不通”和“说话能不能变成文字”。

范围：

- 主页增加“语音可用性”；
- 增加“试说一句”测试输入框；
- 诊断功能改名为“测试声音通道”，主页只复用快捷入口；
- 显示等待遥控器、声音到达、文字变化和失败下一步。

暂不包含：连续听写、自动路由、长期统计和任意外部输入框读取。

### 阶段 B：会话健康与问题摘要

用户结果：失败后能看懂卡在按键、BLE 音频、输出、宿主快捷键还是文字结果。

范围：

- 扩展桥接运行状态；
- 最近会话健康摘要；
- 诊断页详细结果；
- 复制脱敏问题摘要；
- 明确后台恢复原因和次数。

### 阶段 C：语音工具预设与向导

用户结果：第一次安装不再依赖长 README 猜配置，并能完成真实端到端验收。

范围：

- 只收录经过本项目验证的语音工具预设；
- 五步向导复用阶段 A、B 的正式状态；
- 设置变化后主页重新显示缺项，不用单一完成标记掩盖失效。

### 独立研究：连续听写

先做协议和真机证据，不与前三阶段共享交付承诺。通过完整门禁后，再单独讨论是否
增加第二种正式语音生命周期。

### 后续候选

任意 App、本地统计、映射方案和有限组合动作，按真实需求分别立项。文字回眸、MCP、
手机/Watch/网页和自动更新暂不进入当前 Windows RC003 主线。

## 11. 完成度判断

不能简单说对方“全面远超”：

- 言灵在 Windows 用户可用性、真实语音验收、会话健康、输入法预设、连续听写和
  更新体验上明显更完整；这是我们最应该承认和学习的差距。
- 无线麦在产品广度、首次使用、统计、跨设备、回眸和 Agent 生态上更远，但大量能力
  是 macOS 专属、候选或私有组件，不能直接折算成 Windows 可复用完成度。
- 我们在 Windows 13 键补全、Raw Input/HID tap、明确端点选择、不静默改默认设备、
  设置/桥接进程分离和严格构建验证上有自己的深度，并不是从零开始。

真正需要补的不是把两边所有菜单搬过来，而是先完成三个结果：

1. 用户能在主页真实试说一句；
2. 软件能证明声音是否真的到达；
3. 失败后给出唯一、准确的下一步。

完成这三项后，我们与言灵之间最影响日常使用的差距会明显缩小，其它扩展能力再按
真实需求逐项决定。
