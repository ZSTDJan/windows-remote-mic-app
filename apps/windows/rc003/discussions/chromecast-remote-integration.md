## 2. 当前结论

本机已经证明这只遥控器的普通按键数据能够到达 Windows，并能在不启动 BTVS、
Wireshark 或第三方抓包驱动的情况下，由独立诊断程序实时区分。用户实测反馈按键灵敏，
没有可感知延迟；停止后再次开始也能重新确认来源并继续收键。

当前仍不等于已经支持该设备：Remote Mic 正式源码、配置、设备选择、第二映射视图、
手势执行和语音链路均未修改。按键诊断也没有完成跨电脑、不同蓝牙适配器、不同固件、
长期断线恢复和多实体适配器验证。

普通按键与语音是两条独立链路：

1. 普通按键通过 ATT 属性 `0x0029` 发送 8 字节报告；
2. Assistant/语音键通过控制属性 `0x003F` 启停会话，音频通知曾出现在 `0x003C`；
3. 已经确认控制与音频数据曾到达电脑，但尚未完成连续音频解码、有效语音波形和现有
   ATVV 解码器兼容性验证。

## 3. 本机设备事实

- Windows 蓝牙名称：`Chromecast Remote`
- 实测 BLE 地址：仅保留在本机诊断证据中，不公开实体地址。
- HID 标识：VID `18D1`、PID `9450`、版本 `0110`
- 本机 USB 蓝牙适配器：`0A12:0001`，版本 `8891`
- 本机蓝牙地址：仅保留在本机诊断证据中，不公开实体地址。

这些值只描述 2026-09-14 的本机测试对象。正式产品不得把实体地址、连接句柄或属性
句柄当成全部设备通用常量；用户配置也不应持久化诊断抓包中的临时连接句柄。

## 4. 已核实的普通按键协议

普通按下通知位于 ATT 属性 `0x0029`，报告固定为 8 字节：首字节是按键码，后七字节
为零；松开报告为 8 字节全零。以下映射均由用户按明确顺序操作，并与完整抓包对应：

| 物理按钮 | 首字节 |
| --- | --- |
| 电源 | `01` |
| 上 | `03` |
| 下 | `04` |
| 左 | `05` |
| 右 | `06` |
| 确定 | `07` |
| 静音 | `08` |
| 首页 | `0A` |
| 返回 | `0B` |
| 音量加 | `0C` |
| 音量减 | `0D` |
| YouTube | `0E` |
| Netflix | `0F` |
| 输入源（正面右下角） | `11` |

Assistant/语音键不属于这张普通按键表，不能把普通报告中的 `08` 误叫作语音键。
实测两次按语音键分别观察到控制序列：

```text
04 03 02 0B
08
00 02

04 03 02 0C
08
00 02
```

其中 `04` 是音频会话开始，`08` 是麦克风按钮控制，`00` 是停止；最后一个字节中的
会话号会变化。上述解释用于下一步兼容性验证，不代表语音链路已经通过。

## 5. 不依赖 BTVS 的接收方案

独立诊断工具直接订阅 Windows 蓝牙栈的 ETW 提供程序
`{8A1F9517-3A8C-4A9E-A018-4F17A200F277}`，读取事件 402 中的 ACL 数据，再自行完成
L2CAP、ATT 通知和 8 字节报告解析。它不启动、控制或隐藏 BTVS，也不使用
Wireshark、USBPcap 或新内核驱动。

不能只凭旧连接句柄、消息形状、时间接近或“当前只有一个设备”认定来源。当前诊断工具
采用以下只读确认流程：

1. 用户明确选择目标 BLE 地址；
2. 通过 WinRT 对一个每次随机生成、实际不存在的服务 UUID 发起无缓存查询；
3. 同时在 ETW 中找到包含该随机 UUID 的真实出站 ATT 请求；
4. 核对同一连接句柄返回“属性未找到”，并核对 WinRT 查询成功且结果为零个服务；
5. 只有以上条件同时成立，才把该连接句柄绑定为本次所选设备的来源。

该查询不写 GATT 特征、不订阅新通知、不要求设备重新配对，也不依赖设备重连。它只在
一次诊断会话内绑定来源；重新开始时必须使用新的随机 UUID 重新确认。

## 6. 实机验证结果

2026-09-14 的主要实测记录如下：

- `events-20260914_155805_220876.jsonl`：来源确认通过；15 次按下和 15 次松开；应用层
  处理延迟平均约 98 毫秒，最小约 68 毫秒，最大约 142 毫秒。用户反馈灵敏、没有可感知
  延迟。
- `events-20260914_170309_809357.jsonl`：停止控制修复后，4 次按下和松开均收到；停止
  后约 17 毫秒正常退出。
- `events-20260914_170509_892446.jsonl`：同一界面再次开始，约 0.28 秒完成新的来源确认；
  10 次按下和松开均收到；平均处理延迟约 106 毫秒，最大约 140 毫秒；停止后约 7 毫秒
  正常退出，无残留接收进程。
- 当前独立按键工具的 43 项定向测试通过，覆盖报告解码、来源确认、诊断状态、界面逻辑
  和停止控制。

旧诊断工具曾把系统缓冲中的迟到松开误判成长按；该墙钟推断已删除。正式产品接入时应
把原始按下/松开边沿送入 Remote Mic 已有手势引擎，不复制临时诊断工具的长按逻辑。

## 7. 正式接入边界

正式接入时至少遵守以下边界：

1. **用户明确选择设备。** 识别到多个可支持设备不能让软件不可用，也不能由程序私自
   决定最终使用哪一个；当前活动设备由用户选择和确认。
2. **独立第二视图。** Chromecast Remote 使用自己的设备状态、按键测试、映射和语音
   状态视图，不套用或冒充“小米遥控器 2 Pro”页面。
3. **复用现有执行层。** 新设备接收层只输出统一按键边沿，单击、双击、长按、映射保存
   与动作执行继续复用 Remote Mic 的现有逻辑。
4. **设备故障隔离。** 未连接、未授权、来源确认失败或语音不兼容时，只影响该设备；
   不能阻断 RC003、普通快捷键或程序启动。
5. **配置隔离。** 两种遥控器保留各自的设备身份、按键映射和语音能力状态，切换设备
   不覆盖另一种设备的用户配置。
6. **先验证再宣称支持。** 临时工具通过不等于产品通过；完成正式接入、真实映射执行、
   重启恢复和失败降级实测后，才能修改当前支持设备说明。

## 8. 语音独立验证顺序

语音先在独立工具中验证，不直接接入 Remote Mic。第一阶段只做内存分析，不播放、
不保存录音、不触发输入法或语音应用：

1. 使用与按键工具相同的随机服务查询确认数据属于用户选择的遥控器；
2. 分别统计 `0x003F` 控制通知和 `0x003C` 音频通知；
3. 核对按住 Assistant、说话、松开的开始—音频—停止顺序；
4. 把音频数据仅在内存中交给现有 ATVV 解码器，记录时长、包数、样本数、峰值和
   RMS，确认不是空流、固定值或明显破损；
5. 结束立即丢弃音频样本，日志只保留协议状态和统计量；
6. 只有该阶段通过，才讨论可听回放、临时 WAV、正式传声或输入法联动，且这些都需要
   单独确认。

第一阶段要分别给出三项结论：控制事件是否到达、音频数据是否到达、现有解码器是否能
得到合理 PCM。任一项失败都不得用另外两项代替。

## 9. 权限、安装与发布约束

当前 ETW 实时工具需要管理员权限，并依赖系统注册表中的
`EtwLogSensitiveData=1`。该值是本机此前使用 BTVS 完整包日志时留下的全局敏感日志
开关；独立工具只检查，不会设置或恢复它。正式产品若采用这条路线，必须另行设计：

- 用户按需安装或启用，而不是让所有用户默认承担权限与日志影响；
- 明确启用前状态、退出和卸载后的恢复规则；
- 不把原始蓝牙包、语音、密钥或设备令牌写入应用日志；
- 评估管理员启动、签名、安装包、系统版本和企业安全策略；
- 把可选采集组件失败限制在 Chromecast Remote 功能内。

当前免 BTVS 诊断路线不复制 Microsoft BTP/BTVS 文件，因此没有把 BTP 再分发许可带入
产品的问题。它仍不是已批准的发布方案；正式打包前要重新完成安全、安装、许可和系统
兼容性审查。
